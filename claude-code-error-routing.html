Claude Code 的错误分流：一次失败的五种归宿

它不做"错误分类学"，只做一件事：把每个失败分配给唯一有能力修它的那一方
🎯 一句话：Claude Code 从不论错误的严重程度，只问一个问题——谁能修？ 模型能修就写成数据，代码能修就静默重来，谁都修不了才停。
最反直觉的是：同一个失败要经过最多四层翻译才落到你眼前，而"停下来"永远是最后一个选项。

① 打个比方：急诊分诊台

病人推进来，分诊护士第一句话不是"病情多危险"，而是"这个该谁接手"。轻重不是判据，谁能接才是。

· 自己能处理（清创、输液）→ 当场处理，病人家属甚至不知道出过状况
· 得转专科（写会诊单交上去）→ 这叫"把信息交给有能力的人"
· 治不了（设备不够、超出本院范围）→ 上报，而且必须如实写清病因
· 还有一类：旁边科室的仪器坏了 → 记一笔，不影响这个病人

Claude Code 的错误处理就是这张分诊台。它只干三件事：判断谁能修、把信息翻译成那一方能用的形式、修不了就诚实上报。

② 五种归宿：一张图看完

失败一发生，就按"在哪一层出的事"分流。注意每一行的可见性完全不同——有的模型知道、用户不知道；有的两边都不知道。

工具is_error: true命令非零退出 / 文件不存在 / 权限拒绝 / MCP 挂了 → 变成一条工具结果。模型看得见，这就是给它的
传输withRetry429 限流 / 529 过载 / socket 断 / token 过期 → 退避重试或刷新凭证，模型完全不知道
协议withhold输出截断 / 上下文超限 / 钩子打回 → 先扣留，内部恢复，用户看不见
装配void钩子自己崩了 / 记忆提取崩了 / 压缩连续失败 → 记日志当没发生，最多一条 warning
致命return鉴权彻底失败 / 非法请求 / 内部 bug → 终止，而且报真实错误
绿＝本来就该这样；橙＝都有代价（重复请求 / 扣留 / 静默吞掉 / 直接死）。唯一"零代价"的那一行不存在。
装配层那行有个默认值值得记：Stop hook 自己崩了，代码返回的是"放行"（blockingErrors: [], preventContinuation: false）。基础设施出错时，选最不打扰使用者的那条路。

为什么偏偏只有工具层把错误"交出去"？因为它是唯一错误本身就是信息的层：文件不存在，它才会换一个路径；命令报错，它才会改参数。所以这条错误必须是可行动的——"文件不存在，最接近的是 src/Query.ts"，远好于一整段调用堆栈。堆栈是写给工程师看的，它不是。

③ 三种"修法"：区别不在谁动手，在历史变没变

很多人以为"代码修"和"交给模型"没区别——反正最后都要再发一次请求。区别在这儿：

①历史一字不改纯重试：[U1, A1, U2] → 原样再发。模型看到的输入和它从未失败过完全相同，它不知道有这回事
②历史变了，没加错误无感替换：[摘要, A1, U2] → 压缩 / 切 fallback 模型 / 8k→64k。模型不知道为什么会变，只是从新起点重来
③历史多一条告知：[..., tool_result(is_error)] → 模型必须改计划，因为它的世界线里出现了一个新事实
②最容易被忽略：请求确实又发出去了，但那不是"模型在处理错误"，而是错误的成因被消掉了。
所以判据不是"交给谁"，而是"这次失败要不要算数"。算数才写进历史——因为只有模型能改变自己下一轮的行为。

③ 的代价是三重的：错误一旦进历史就每轮都要重新付费，直到被压缩掉为止；模型会被这条信息带偏，可能在后面几轮反复纠结它；最糟的是有些错误越告知越严重——413 就是标本，喂回去只会让下一次更快撞墙。所以③是最贵、最慢、影响最久的一档，不是安全的默认档。

④ 两条硬边界：决定走哪条路

把上图的五种归宿压成一句判断，只需要问两个问题。第二条比第一条更硬：

失败发生 → 谁能修？
① 与输入无关（瞬时）→ 直接重试　[429 / 529 / socket / token]
前提：输入逐字节相同 ⇒ 同一模型输出分布也相同
② 与输入有关，但代码能改 → 改掉成因再试　[压缩 / 切模型 / 调大上限]
例：输入太长 → 压短它，而不是重发同一个
③ 与输入有关，只有模型能改 → 写进历史　[文件不存在 / 命令报错]
反例：413「喂回去会增加触发条件」→ 只会更快再撞一次
④ 谁都改不了 → 终止　[鉴权失败 / 非法请求 / 内部 bug]
模型读一百遍也改不了，喂进去只是烧 token

第一条尺子是"失败与输入有关吗"——输入一样的重试注定失败，所以 withRetry 只重试 429/529/网络，绝不重试 400。

第二条尺子更硬：能重试的边界 = 副作用边界。模型生成没有副作用，浪费了重来即可；工具执行有副作用（文件已写、命令已跑），没法假装没发生。所以工具失败一律走③。

还有一条不成文但更冷的尺子：值不值得重试，取决于有没有人在等。只有前台会话（FOREGROUND_529_RETRY_SOURCES）才重试 529；生成摘要、起标题、跑分类器这些后台调用立刻放弃。因为容量雪崩时每一次重试都会把网关压力放大 3–10 倍，而这些结果此刻没人在盯着——重试一个没人等的请求，是纯浪费。

⑤ 终止之前：先把历史修成合法的

决定放弃的那一刻，还有两件必做的事。这是"异常安全"——可以失败，但不能留下一段别人再也用不了的数据。

❌ 直觉做法

出错了？抛出去、打印、进程退出。历史先不管。

结果：历史里留下一个没有配对的 tool_use。API 要求每个 tool_use 必须有对应的 tool_result，所以从这一刻起整段对话都是非法请求，/resume 拉回来也照样 400。

✅ 实际做法

① yieldMissingToolResultBlocks：给每个没执行的 tool_use 补一条"未执行"的结果。

② 报真实错误。旧版会伪装成"用户中断"，结果 SDK 用户看到一堆幻影 interrupt，真正的 bug 被埋了几个月。

这条规则的本质是：可以失败，但不可以留脏数据。崩溃是局部事故，脏数据是永久污染——前者重启一下就好，后者让这段对话再也恢复不了。所以退出路径上的清理，优先级高于"退得体面"。

⑦ 三个反直觉的地方

反直觉一
以为：错误越严重越该上报。
实际：越"没人能修"的才上报。最"严重"的上下文爆掉，反而被完整扣留、静默抢救——因为代码真的能修。
反直觉二
以为：重试就是"再试一次"。
实际：输入一样的重试注定失败。重试只对"与输入无关"的失败有效，这是它能成立的前提，不是技巧。
反直觉三
以为：告诉模型它就能修。
实际：错误进历史是永久的，每一轮都重新付费；还会把模型带偏——给它 ECONNRESET，它开始"诊断网络"。
常见误解
"崩了就结束了。" 不。崩溃前必须把数据结构修合法。可以失败，不可以留脏数据——这两件事的优先级是反的。

谁能修就给谁 · 谁都修不了就停 · 停之前先把历史修成合法的
跳出细节看职责边界：这套东西不是在给错误分级，而是在分配修复责任。它不判断"这个错有多糟"，只判断"这件事该由谁接手"。所以整份代码里没有一个"严重程度"字段——只有层、边界、和次数上限。这也是为什么通读它的错误处理会觉得"散"——它本来就不是一套分类学，而是一串责任交接点：每一处 catch 都在回答同一句话，下一个该谁。
