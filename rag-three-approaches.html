普通 RAG、Agentic RAG 与当前 Read 方案：差在谁来决定检索

名字只差一个词，定位差一整个架构——一期没有 Chunk、Embedding、向量库，它用 50 行预览、临时文件和 grep 换多轮取证，准确的名字是 Agentic Retrieval。
🎯 一句话：决定检索的人是谁，比有没有向量库更能定义一套方案是不是 Agentic。
当前 Read 方案已经把决定权交给了 Agent，代价是召回靠关键词——所以它是Agentic Retrieval，不是完整的 Agentic RAG。

一、先把三种方案摆在一起

三者不是同一条升级链上的三档，而是三种分工：谁决定检索、检索跑几次、跑完由谁判断够不够。看第二列就够了。

方式谁决定检索检索过程适用场景
普通 RAG固定程序一次 Query → Top-K → GenerateFAQ、稳定知识库、单跳问题
Agentic RAGAgent拆题、路由、检索、评价、改写、再检索多跳问题、多数据源、复杂调研
当前 Read 方案Agent + 文件工具Preview → grep → Range Read，可循环一次性长文件、日志、代码、明确关键词

第三行不是类比，是代码里真实跑的一条路径：50 行阈值、Session 临时文件、snapshot_id、按命中位置读取。下面把它拆开看。

三、当前 Read 方案怎么跑

先讲它为什么存在：原逻辑把文件全文当 Tool Result 返回，遇到约 200k 文本时，上下文、推理、系统、失败四种成本会同时放大。于是 Read 的职责从"把文件返回"变成——在权限、文件版本、任务意图和 Token 预算的约束下，逐步提供足够且可追溯的证据。

判定50 行阈值未超阈值直接完整返回，不引入任何额外开销
预览前 50 行先给结构和开头，让 Agent 想清楚要搜什么
落盘Session 临时文件全文保留可寻址，模型只拿到句柄和引用
定位grep关键词由 Agent 自己生成，命中位置清楚可解释
取证Range Read只读命中位置附近的片段；不够就改写查询再来
五个动作串起来，就是"观察 → 决定 → 读取 → 判断"的循环。
这不是简单截断。普通截断把后半段永久丢掉；当前方案保留可寻址全文，本质是把一次性推送改成按需拉取。它和 ReAct 的"推理与行动交错"同构，和 Self-RAG 的"按需检索 + 自我评价"同向，差别是评价发生在 Agent 的循环里，而不是模型内部的反思 token。
Agentic RAG 的完整形态
检索决定权在 Agent —— 已有 ✓
Chunk 切块 —— 一期未确认 ✗
Embedding 向量化 —— 一期未确认 ✗
向量库 / 索引召回 —— 一期未确认 ✗
红框不是"做得差"，是"这套方案里根本没有这个零件"。名字要跟着零件走。

四、返回协议：让 Agent 的下一步可计算

Read 返回的不是一段文本，而是一个带状态的引用。字段设计的目标只有一件事：让 Agent 能判断"还有多少没看、行号会不会漂、下一步该怎么查"。

字段它解决什么问题
status = truncated显式声明被截断；静默截断会让模型误以为看到了全文
file_handle不透明句柄，不把真实磁盘路径暴露给模型
snapshot_idSearch 与 Range Read 绑定同一快照，防止两次调用间文件被改导致行号漂移
total_bytes / total_lines让 Agent 知道全文规模，判断要不要继续挖
estimated_tokens比行数更贴近真实的上下文压力
returned_range本次实际返回的行区间，和 grep 命中对齐
suggested_actions提示下一步可用 search / read_range
expires_at引用带 TTL，并绑定 tenant / workspace / session
最容易出错的一条是 snapshot：没有它，Agent 上一轮 grep 拿到的行号和这一轮读到的内容可能对不上，错得还很隐蔽。文件引用必须绑定租户、工作区、会话和 TTL，否则临时文件会变成跨会话的泄漏面。

五、省了多少：按 200k 中文字符算

按原文的容量模型：200k 中文字符约 18 万 Token，预览 50 行、两轮检索、每轮 4 个 15 行片段。结果是——

94.5%理论 Token 节省率（中心测算）
9,980新方案进入上下文的 Token 估算
3–5 次Tool 调用次数，原方案为 1 次

原方案：200,000 字符 × 0.9 ≈ 180,000 Token

预览：50 行 × 60 字符 × 0.9 ≈ 2,700

局部证据：2 轮 × 4 片段 × 15 行 × 60 字符 × 0.9 ≈ 6,480

查询与 Tool 元数据：约 800

合计 9,980，节省率 = 1 − 9,980 / 180,000 ≈ 94.5%。代价是 Tool 调用从 1 次变成 3～5 次。

对外口径是 85%～95%，且只适用于关键词定位类的长文档任务；全文摘要、风险穷举这类需要完整覆盖的任务不适用。这是容量测算，不是线上实测。

50 行是"开销最小的工程止血"，不是理论最优——单行 JSON 或压缩文本仍可能很长，关键内容也可能不在开头。演进方向是动态预算：

B_read = min(B_read_max, floor(ρ × B_available))

六、代价：grep 的强项与盲区

这套方案强在精确、便宜、位置清楚；弱在字面匹配，换个说法就接不住。

✅ 能命中

日志、代码、错误码、Trace ID、函数名、合同编号——这些是唯一 token。

无需预建索引、时延与成本低、命中位置可解释、可复用 Agent 已有原子工具、文件更新后不用处理索引一致性。

代价：只认字面，同义词和概念问法接不住。

⚠️ 会漏

同义词、OCR 错字、概念性问题可能零命中；PDF 转文本后行结构未必稳定；单个片段缺少跨段上下文。

更关键的是：Top-K 命中无法证明"全文不存在某项内容"。

代价：得补 BM25 / Embedding，或为否定性结论走完整扫描。

所以一期是低成本基础路径，不是所有检索问题的最终解。常见失败模式与对策如下（原文第 10 节）：

失败模式表现处理方式
前 50 行没有代表性关键内容在中后部同时提供目录、尾部和结构采样
单行超长50 行仍爆 Token增加单行字节和 Token 上限
grep 零命中同义词或 OCR 错字查询扩展，必要时转 BM25 / Embedding
命中太多Search 再次撑爆上下文Top-K、分页、总命中数、is_capped
片段太窄有关键词但语义不完整按段落 / 标题扩窗，合并相邻区间
文件在调用间变化引用和行号失效不可变 Snapshot 与版本冲突检查
检索无限循环成本和延迟失控轮数、Token、Deadline 三重预算
临时文件泄漏跨 Session 访问不透明句柄、租户鉴权、TTL、回收
文档 Prompt Injection内容诱导 Agent 越权正文视为不可信数据，权限仍由 Runtime 决定

七、往哪演进：Agentic Retrieval Router

不是"以后都上向量"，而是按任务类型路由到最便宜的检索方式。

任务类型首选检索原因
Trace ID、错误码、函数名literal / grep精确、便宜
组合条件regex、关键词扩展不需要索引
标题、页码、函数、Sheet结构化索引保留原文结构
同义表达、概念问答BM25 或 Embedding弥补字面不匹配
跨章节、多跳问题查询拆解 + 多轮取证单次 Top-K 证据不全
全文摘要、合规穷举流式扫描或 Map-Reduce检索无法证明覆盖完整

循环还得有明确的退出规则，否则成本和延迟都会失控：

证据每个子问题都已经拿到可定位的证据
轮数达到最大轮数
预算达到总 Token 或 Tool 预算
增量连续一轮没有新增证据
覆盖任务需要完整覆盖时，切换到 exhaustive 模式
特别注意："没有检索到"不等于"文档中不存在"。否定性结论必须基于完整扫描或可证明覆盖的索引。

八、记住这一句

决定权在 Agent，证据落在行号——这就是 Agentic Retrieval。

  2. 为什么"grep 零命中"不能作为"文档里没有"的证据？

三者的关系不是升级链条，而是三种分工：普通 RAG 把检索固化进程序；Agentic RAG 把检索交给 Agent 并配齐 Chunk、Embedding、向量库；当前方案把决定权交给了 Agent，但没配三件套，靠 50 行预览、临时文件和 grep 完成多轮取证——所以它准确的名字是 Agentic Retrieval。这个选择在眼下是合理的：一次性长文件、日志、代码本来就是关键词检索的主场。等要跨文档、要语义模糊的召回时，再补那三件、上 Router，也不迟。
