## 0. 一张表说清区别（先记住这个）

假设你查的是 `user:10086`：

| | 缓存里有吗 | DB 里有吗 | 触发条件 | 请求特征 |
|---|---|---|---|---|
| **穿透** | 没有 | **也没有** | 查一个**根本不存在**的数据 | 持续、可被恶意构造、每次都绕过缓存 |
| **击穿** | 没有（**刚过期**） | **有** | 一个**热点 key 恰好过期** | 瞬间高并发，全部打向 DB 查同一行 |
| **雪崩** | 大量没有 | 都有 | **大量 key 同时失效**或 **Redis 挂了** | 全面性、系统性，DB 瞬间被压垮 |

一句话记忆：

> **穿透 = 查不存在的；击穿 = 一个热点没了；雪崩 = 一片都没了。**

再补一个最容易混的点：

> **击穿和雪崩的区别不是“量”，而是“原因”**——击穿是**单个**热点 key 失效，雪崩是**大批量** key 同时失效或缓存整体不可用。有些资料把“热点 key 被超高并发访问”直接叫击穿，其实那是“热点 key 问题”，本质不同。

## 1. 缓存穿透（Cache Penetration）

### 1.1 是什么

请求查询一个 **缓存和数据库都不存在** 的数据。

正常的缓存流程是：

```
查缓存 → 命中就返回
       → 没命中 → 查 DB → DB 有 → 写回缓存
                        → DB 没有 → 什么都不写 → 直接返回空
```

问题就在最后一行：**DB 没有的数据不会被缓存**，所以下一次同样的请求，**还是会走完整流程打到 DB**。

```
请求 id = -1（不存在）
  → 缓存 miss
    → DB miss
      → 返回 null（缓存里依然什么都没有）
        → 下次请求 id = -1 还是一样的流程
```

**如果攻击者用脚本每秒发 10 万个不存在的 id，DB 就要承受 10 万 QPS 的无效查询。**

### 1.2 三种成因（面试能多说一种就加分）

| 成因 | 说明 |
|---|---|
| **恶意攻击**（最常见） | 用不存在的 ID 遍历，打垮数据库 |
| **业务代码 bug** | 参数没校验，`id = null` 变成 `where id = null` 查不到；或 ID 生成器产生脏数据 |
| **数据被删除/迁移** | 缓存和 DB 都没了，但上游还在按旧 ID 请求 |

### 1.3 方案一：缓存空值（最简单，但要处理细节）

```java
public User getUser(Long id) {
    String key = "user:" + id;
    String cached = redis.get(key);
    if (cached != null) {
        return "NULL".equals(cached) ? null : JSON.parse(cached);
    }

    User user = db.queryById(id);
    if (user == null) {
        // 关键：把"空"也缓存起来，但要短 TTL
        redis.setex(key, 60, "NULL");   // 60 秒
        return null;
    }
    redis.setex(key, 3600, JSON.toJSONString(user));
    return user;
}
```

**四个必须注意的细节（答出来显得你真写过）：**

| 细节 | 原因 |
|---|---|
| **TTL 要短**（30~120 秒） | 太长会导致"数据后来真的插入了，但缓存还是空"的脏读 |
| **用特殊标记值**（如 `"NULL"` 或 `"{}"`） | 直接存空字符串会与真实空值混淆，也便于批量清理 |
| **key 加前缀区分**（如 `null:user:10086`） | 便于用 `SCAN` 批量清理，也便于监控 |
| **数据写入时要主动删空值 key** | 否则新数据要等 60 秒才能被查到（这是最常被追问的点） |

**致命局限**：如果攻击者用**随机且大量**的 ID，每次 key 都不同，空值缓存会**把 Redis 内存打满**——这时空值缓存反而成了帮凶。
→ 所以空值缓存只能防"重复查同一个不存在的 key"，防不了随机攻击。**随机攻击要用布隆过滤器 + 限流。**

### 1.4 方案二：布隆过滤器（Bloom Filter，标准答案）

**原理**（面试必须能画出来）：

```
一个 m 位的位数组（初始全 0）+ k 个独立的哈希函数

写入 "user:10086"：
  h1("user:10086") % m = 3   → bit[3] = 1
  h2("user:10086") % m = 9   → bit[9] = 1
  h3("user:10086") % m = 17  → bit[17] = 1

查询 "user:10086"：看 bit[3]、bit[9]、bit[17] 是否全为 1
  → 全为 1 → "可能存在"（有误判）
  → 有任何一个为 0 → "一定不存在"（100% 准确）
```

**关键性质（这是它为什么能解决穿透的原因）：**

| 性质 | 说明 |
|---|---|
| **能确定“不存在”** | 只要有一个 bit 是 0，就 100% 不存在 → **可以直接拦截，不打 DB** |
| **不能确定“存在”** | 全为 1 只说明“可能存在”，可能误判（假阳性） |
| **不存在假阴性** | 存在的元素一定不会被判为不存在 |
| **不支持删除** | 把 bit 置 0 会影响其他元素 |

**参数怎么定（能报数字是加分项）**

误判率公式：

```
p ≈ (1 - e^(-k·n/m))^k

n = 元素个数，m = 位数组位数，k = 哈希函数个数
最优 k = (m/n) × ln2 ≈ 0.693 × (m/n)
```

实测算例：**1 亿条数据，每个元素分配 10 bit**

```
m = 10 亿 bit = 125 MB
k = 10 × 0.693 ≈ 7
p = (1 - e^(-0.7))^7 ≈ 0.8%
```

也就是说：**125MB 内存，就能把 1 亿个 key 的穿透拦截在 99.2% 以上**。这个性价比极高，也是布隆过滤器被广泛使用的根本原因。

**生产落地的四个坑（这才是加分部分）：**

| 坑 | 说明 |
|---|---|
| **数据同步** | 布隆过滤器要在应用启动时预热（从 DB 全量加载），新增数据要实时 `add` 进去 |
| **不支持删除** | 数据删了过滤器的 bit 还在 → 会放行已删除的 ID。解决：用**计数布隆**（每位换成计数器，占 4 倍空间）或 **Cuckoo Filter**（支持删除，RedisBloom 模块提供） |
| **扩容难** | 位数组一旦定死，数据量涨了就误判率上升。解决：**分层布隆**（多个过滤器串联，新的放新过滤器） |
| **误判率的业务含义** | 0.8% 的误判 = 每 1000 次不存在查询，仍有 8 次打到 DB。可接受；如果追求更低，加位数（每元素 14 bit → 误判率降到 0.01%） |

**实现方式**：

```java
// 本地：Guava
BloomFilter<String> filter = BloomFilter.create(Funnels.stringFunnel(), 100_000_000, 0.008);
filter.put("user:10086");
if (!filter.mightContain("user:" + id)) {
    return null;   // 一定不存在，直接返回
}
// 可能存在 → 继续查缓存和 DB
```

分布式场景用 **RedisBloom 模块**（`BF.ADD` / `BF.EXISTS`），或自己用 Redis 的 bitmap 实现。

### 1.5 方案三：兜底防线

| 手段 | 说明 |
|---|---|
| **参数校验** | ID 必须是正整数、长度校验、格式校验（第一道防线，成本最低） |
| **限流** | 单 IP / 单用户 QPS 限流，把攻击量级压下来 |
| **黑名单** | 拦截已知恶意 IP/UA |
| **鉴权** | 必须登录才能查，提高攻击成本 |

### 1.6 一句话总结

> **穿透的本质是「无效查询绕过了缓存直达 DB」。空值缓存解决“重复的无效查询”，布隆过滤器解决“随机的无效查询”，限流解决“高频的无效查询”——三者是互补而非替代关系。**

## 2. 缓存击穿（Cache Breakdown / Hotspot Invalid）

### 2.1 是什么

**一个被高频访问的热点 key，在过期的那一瞬间，大量并发请求同时发现缓存失效，全部去查 DB。**

```
t=0    热点 key 存在，QPS 10万全部命中缓存  ✅
t=100  热点 key 过期（TTL 到了）
t=100.001  1 万个并发请求同时 miss
           → 1 万个请求同时查 DB 查同一行
           → DB 瞬间被这一个查询打满
```

**和穿透的核心区别：**

| | 穿透 | 击穿 |
|---|---|---|
| key 在 DB 里 | **不存在** | **存在** |
| 失效原因 | 从来没被缓存 | **刚好过期** |
| 请求特征 | 持续、分散 | **瞬间、集中**在同一个 key |
| 本质问题 | 无效查询 | **缓存重建的并发控制** |

> 注意：**击穿的前提是“热点”**。一个每天只被查 3 次的 key 过期了，根本不算击穿。

### 2.2 方案一：互斥锁重建（最常考）

**思路**：缓存失效时，**只允许一个线程去查 DB 并重建缓存，其他线程等待**。

```java
public User getUser(Long id) {
    String key = "user:" + id;
    User cache = getFromCache(key);
    if (cache != null) return cache;

    // 分布式锁，只有一个人能重建
    String lockKey = "lock:user:" + id;
    boolean locked = redis.set(lockKey, "1", SetArgs.setParams()
                                   .nx().px(3000));   // NX + 3s 过期
    if (locked) {
        try {
            // 双重检查：可能前一个持锁线程已经建好了
            cache = getFromCache(key);
            if (cache != null) return cache;

            User user = db.queryById(id);
            if (user != null) {
                redis.setex(key, 3600, JSON.toJSONString(user));
            }
            return user;
        } finally {
            // 必须用 Lua 校验 value，防止误删别人的锁
            unlockSafely(lockKey);
        }
    } else {
        // 没抢到锁 → 短暂等待后重试（或返回降级数据）
        Thread.sleep(50);
        return getUser(id);   // 递归重试，注意加次数限制！
    }
}
```

**五个必须注意的细节（每一条都是面试深挖点）：**

| 细节 | 为什么 |
|---|---|
| **双重检查（double check）** | 抢到锁后要再查一次缓存，否则会在别人已经建好后重复查 DB |
| **锁必须有过期时间** | 否则持锁线程挂了 → 死锁 → 整个 key 永久不可用 |
| **释放锁要用 Lua 校验 value** | 否则如果业务执行超过锁超时，可能删掉别人的锁 |
| **等待方要有重试上限** | 上面的递归如果 DB 一直慢，会无限递归 → 栈溢出 |
| **锁粒度要细** | 锁 `lock:user:10086` 而不是 `lock:user`，否则不同 key 互相阻塞 |

**缺点（一定要说出来）：**

- **牺牲了可用性换一致性**：等待方会阻塞，RT 上升
- **吞吐下降**：本来 1 万个并发，现在串行
- **如果 DB 已经慢**，持锁线程迟迟不释放 → 大量线程等待超时 → 体验极差

### 2.3 方案二：逻辑过期（Logical Expire）—— 生产更常用

**思路**：**Redis 的 key 永不过期**，把过期时间写在 value 里，由业务自己判断。发现"逻辑过期"时，**返回旧值 + 异步刷新**。

```java
// value 结构
class CacheWrapper<T> {
    T data;
    long expireAt;   // 逻辑过期时间戳
}

public User getUser(Long id) {
    String key = "user:" + id;
    CacheWrapper<User> wrapper = getFromCache(key);

    if (wrapper == null) {
        // 真的没缓存过（冷启动），走同步加载
        return loadAndCache(id);
    }

    if (wrapper.expireAt > System.currentTimeMillis()) {
        return wrapper.data;              // 未过期，直接返回
    }

    // 已逻辑过期 → 返回旧值，同时异步刷新
    if (refreshLock.tryLock()) {          // 本地锁，防止重复提交刷新任务
        try {
            refreshPool.execute(() -> {
                try {
                    User fresh = db.queryById(id);
                    redis.set(key, new CacheWrapper<>(fresh, now + 3600_000));
                } finally {
                    refreshLock.unlock();
                }
            });
        } catch (RejectedExecutionException e) {
            refreshLock.unlock();          // 池满就放弃本次刷新
        }
    }
    return wrapper.data;                   // 关键：立刻返回旧数据，不等刷新
}
```

**优点**：

| 优点 | 说明 |
|---|---|
| **永不阻塞** | 所有请求立刻返回，无等待 |
| **高可用** | DB 挂了也能返回旧数据（降级能力） |
| **吞吐高** | 没有串行化 |

**缺点**：

| 缺点 | 说明 |
|---|---|
| **数据可能短暂不一致** | 返回的是旧值，业务要能接受 |
| **实现复杂** | 需要额外线程池、需要处理刷新失败 |
| **冷启动问题** | 缓存里没有时还是要同步加载（所以大促前要预热） |
| **内存不释放** | key 永不过期 → 需要额外的淘汰机制（配合 `allkeys-lru`） |

**这是电商详情页、商品信息、配置类数据的标准做法**——这些数据"旧几秒钟"完全可接受，但"卡住 3 秒"不可接受。

### 2.4 方案三：热点 key 永不过期 + 后台定时刷新

最朴素也最有效：

```
定时任务/延迟队列 每 5 分钟刷新一次热点 key
key 不设 TTL，靠主动更新保证新鲜度
```

适用：**明确知道哪些是热点**（首页推荐、活动配置、秒杀商品）。

### 2.5 方案四：提前预热（大促必备）

```
大促开始前 30 分钟：
  扫描预期热点数据 → 批量写入 Redis → 设置不同 TTL
  保证大促期间不会出现"冷启动击穿"
```

这是**工程上最有效、成本最低**的手段，但很多候选人想不到。

### 2.6 一句话总结

> **击穿的本质是「缓存重建瞬间的并发失控」。互斥锁是“让一个人去建，其他人等”，逻辑过期是“先用旧的，后台慢慢建”——前者强一致低可用，后者高可用弱一致。**

## 3. 缓存雪崩（Cache Avalanche）

### 3.1 是什么

**大量缓存 key 在同一时间失效，或者 Redis 整个不可用，导致所有请求涌向 DB。**

要分成两种子类型讲，很多人只讲第一种：

### 3.2 类型一：大量 key 同时过期（可预测、可预防）

**成因**：

```java
// 典型错误写法：所有 key 都是 1 小时
redis.setex(key, 3600, value);
```

如果系统在凌晨 2 点做了一次**批量预热**，那所有 key 都会在凌晨 3 点**同时过期** → 整点雪崩。

**方案 1：TTL 加随机抖动**（必答，成本最低）

```java
int base = 3600;
int jitter = ThreadLocalRandom.current().nextInt(0, 600);   // 0~10 分钟
redis.setex(key, base + jitter, value);
```

把过期时间**打散到一个时间窗口内**，避免同一秒集中失效。

**方案 2：分级 TTL**

```
核心数据：2 小时 + 随机 10 分钟
普通数据：30 分钟 + 随机 5 分钟
```

不同业务用不同的基础时间，进一步打散。

### 3.3 类型二：Redis 不可用（更严重，要讲架构）

**成因**：

| 场景 | 说明 |
|---|---|
| Redis 单点宕机 | 没做主从/哨兵 |
| 主节点故障切换 | 切换期间（几秒~几十秒）缓存全不可用 |
| 内存打满被 OOM Killer 杀 | 没设 `maxmemory` 或淘汰策略是 `noeviction` |
| 网络分区/抖动 | 应用连不上 Redis |
| 大 key 阻塞 | 一次 `keys *` 或 `del` 大 key 把主线程卡住 |

**这时候的正确思路非常重要：**

> **不要试图让 DB 接住全部流量**（它接不住），而是**主动限流 + 降级**，牺牲一部分请求，保住 DB 不被打挂。**这是"可用性降级"而不是"性能优化"。**

**方案组合：**

| 层次 | 手段 | 说明 |
|---|---|---|
| **架构层** | 主从 + 哨兵 / Cluster | 消除单点，故障自动切换（3 哨兵、3 主 3 从） |
| | 持久化 | 重启后能快速恢复数据，不用全量回源 |
| | 多可用区部署 | 防机房级故障 |
| **应用层** | **本地缓存兜底**（Caffeine） | Redis 挂了，本地还有一份热点数据，能挡住 80% 流量 |
| | **熔断** | 检测到 Redis 连续失败 → 直接快速失败，不重试（避免每个请求都等 2 秒超时） |
| | **限流** | 对回源 DB 的流量限流（如 Sentinel 控制 QPS 到 DB 承受上限） |
| | **降级** | 非核心数据返回默认值/空对象（如"暂时无法显示"） |
| | **连接超时设短** | Redis 客户端 `timeout` 设 200~500ms，别设 2 秒，否则线程全被拖死 |
| **运维层** | 监控告警 | 内存水位、命中率、连接数、RT |
| | 容量预留 | `maxmemory` 只配 60%，防 OOM |
| | 大促前压测 + 预热 | 提前暴露问题 |

**多级缓存的栈（这是雪崩最有效的纵深防御）：**

```
请求
 ↓
① 本地 Caffeine（命中率 20%~40%，零网络开销）
 ↓ miss
② Redis 集群（命中率 95%+）
 ↓ miss
③ DB
```

Redis 挂了，本地缓存**至少还能顶一段时间**（Caffeine 的 `expireAfterWrite` 设 1~5 分钟），给运维争取恢复时间。

```java
Cache<String, String> localCache = Caffeine.newBuilder()
    .maximumSize(100_000)
    .expireAfterWrite(5, TimeUnit.MINUTES)
    .recordStats()                 // 开统计，看命中率
    .build();
```

**代价**：多实例之间本地缓存不一致 → 用**广播失效**（Redis Pub/Sub、MQ）或**短 TTL 兜底**。

### 3.4 一句话总结

> **雪崩的本质是「缓存层集体失效，压力全部转移到 DB」。同时过期用 TTL 抖动解决（预防），Redis 宕机用多级缓存 + 熔断限流降级解决（兜底）——前者是优化，后者是保命。**

## 4. 三者关系总览（这张图能画出来就稳了）

```
                     请求
                       ↓
          ┌────────────────────────┐
          │ ① 入口层                │  ← 防【穿透】
          │ 参数校验 / 限流 / 鉴权   │
          │ 布隆过滤器               │
          └───────────┬────────────┘
                      ↓
          ┌────────────────────────┐
          │ ② 本地缓存 Caffeine     │  ← 防【雪崩】(Redis 宕机兜底)
          └───────────┬────────────┘
                      ↓ miss
          ┌────────────────────────┐
          │ ③ Redis                │
          │ 空值缓存        ← 防穿透 │
          │ 互斥锁/逻辑过期 ← 防击穿 │
          │ TTL 抖动        ← 防雪崩 │
          └───────────┬────────────┘
                      ↓ miss
          ┌────────────────────────┐
          │ ④ 熔断 / 限流           │  ← 防【雪崩】打挂 DB
          └───────────┬────────────┘
                      ↓
                     DB
```

**防御层次对应关系：**

| 问题 | 主防线 | 备选 |
|---|---|---|
| 穿透 | 布隆过滤器（入口） | 空值缓存、参数校验、限流 |
| 击穿 | 互斥锁 or 逻辑过期（缓存层） | 永不过期 + 定时刷新、预热 |
| 雪崩 | TTL 抖动（预防层） | 多级缓存、熔断、限流、降级、高可用集群 |

## 5. 常见追问（面试官很爱挖这些）

**Q1：布隆过滤器为什么不能删除元素？**
> 因为多个元素共享同一批 bit。你把某元素的 3 个 bit 置 0，可能会把另一个元素的 bit 也清零 → 产生**假阴性**（存在的元素被判为不存在），这比误判更严重。
> 解决：计数布隆（每位用计数器，删除时减 1，占 4 倍空间）或 Cuckoo Filter（RedisBloom 支持，可删除、空间效率更高）。

**Q2：互斥锁方案吞吐太低，怎么办？**
> 三个方向：① 热点数据改用逻辑过期（不阻塞）；② 提前预热 + 永不过期，从根上避免重建；③ 热点 key 探测（如京东 hotkey），把超热 key 自动加载到本地缓存。

**Q3：逻辑过期返回旧数据，业务能接受吗？**
> 看数据类型。商品标题、推荐位、配置类可以（容忍秒级不一致）；库存、余额、订单状态不行（必须强一致 → 走互斥锁或直接读 DB）。**这是设计上的取舍，不是一个方案包打天下。**

**Q4：如果 Redis 整个集群挂了怎么办？**
> 分层兜底：① 本地缓存顶住热点（能挡 20%~40%）；② 客户端快速失败（超时设 200ms，不重试）；③ Sentinel 熔断，对回源流量限流到 DB 承受上限；④ 非核心功能降级返回兜底值；⑤ 核心功能如果必须读 DB，就接受 RT 上升和部分失败——**首要目标是保住 DB 不被打挂**，因为 DB 挂了就是全站瘫痪。

**Q5：这三个问题和「大 key / 热 key」有什么区别？**
> 大 key/热 key 是**数据结构层面的问题**（单个 key 太大或太热导致单分片打满）；三大缓存问题 是**失效时机和并发模式的问题**。两者会互相影响：热 key 过期容易引发击穿，大 key 删除会阻塞主线程进而引发雪崩。

**Q6：为什么说"空值缓存"不能防随机攻击？**
> 因为随机攻击每次都产生**新的 key**，缓存不命中，空值缓存反而会不断写入垃圾数据，**把 Redis 内存打满**，从"穿透"变成"内存打爆"。这种情况必须靠布隆过滤器（O(1) 判断 + 固定内存）+ 限流。

## 6. 30 秒面试话术

> "这三个问题容易混，我先说区别：**穿透是查一个缓存和 DB 都不存在的数据**，每次都绕过缓存打 DB；**击穿是一个热点 key 过期瞬间**，大量并发同时回源查同一行；**雪崩是大量 key 同时失效或者 Redis 整个挂了**，流量全面涌向 DB。
>
> 穿透我用两层：入口做参数校验和限流，核心用**布隆过滤器**——1 亿数据大约 125MB、误判率 0.8%，能在缓存之前拦掉绝大部分无效请求；对重复查同一个不存在 key 的场景再补一层**空值缓存**，注意 TTL 要短、数据写入时要主动删空值。
>
> 击穿的核心是缓存重建的并发控制，两条路：**互斥锁**保证只有一个线程回源，其他人等待，强一致但吞吐低；**逻辑过期**把过期时间写在 value 里、key 永不过期，发现过期就返回旧值并异步刷新，高可用但有短暂不一致。生产上热点数据多用后者，再配合大促前的预热。
>
> 雪崩分两种：**大量 key 同时过期**用 TTL 加随机抖动打散；**Redis 不可用**就要靠架构——主从哨兵或 Cluster 消除单点、本地 Caffeine 做多级缓存兜底、Sentinel 熔断限流降级，核心思路是**牺牲部分请求保住 DB**，而不是让 DB 硬扛。"

---

## 一句话总结

> **穿透是"没有的东西反复查"（用布隆挡），击穿是"有的东西同时查"（用锁或异步挡），雪崩是"全都没有了"（用架构和降级挡）。** 三者防的是三种完全不同的失效模式，所以方案不能互相替代。
