# 第 1 章 · 模型：RabbitMQ 到底长什么样

## 1.1 八个概念，一次讲清

```
Producer
   │  建立 TCP 连接
   ▼
Connection ── 复用出多个 ──> Channel（信道）
   │                            │
   │                            ▼
   │                     ┌──────────────┐
   │                     │   Exchange   │  ← 只做路由，不存消息
   │                     └──────┬───────┘
   │                   Binding + RoutingKey
   │                            ▼
   │                     ┌──────────────┐
   │                     │    Queue     │  ← 真正存消息的地方
   │                     └──────┬───────┘
   ▼                            ▼
                              Consumer
```

| 概念 | 是什么 | 面试要点 |
|---|---|---|
| **Broker** | RabbitMQ 服务进程本身 | 一个 Broker 可含多个 vhost |
| **Vhost** | 虚拟主机，逻辑隔离（类似 MySQL 的 database） | 权限、队列、Exchange 都按 vhost 隔离；多环境/多租户用它隔开 |
| **Connection** | 一条 TCP 连接 | 建立成本高（握手、认证、TLS） |
| **Channel** | 连接上的**虚拟信道**，多路复用 | **所有操作都走 channel**。为什么需要它？避免频繁建 TCP；但 channel 不是线程安全的，**一个线程一个 channel** |
| **Exchange** | 交换机，**只负责路由，不存消息** | 这是 RabbitMQ 最核心也最独特的设计 |
| **Queue** | 队列，真正存消息 | 消费者从 queue 取，**生产者永远不直接发 queue** |
| **Binding** | Exchange 和 Queue 之间的绑定关系 | 可以带 RoutingKey / 参数 |
| **RoutingKey** | 生产者发消息时带的"地址" | Exchange 按它决定投给哪些 Queue |

## 1.2 三个必须内化的认知（这是 RabbitMQ 的灵魂）

**认知 ①：生产者只发 Exchange，不发 Queue。**
Kafka 是"直接写 topic 的某个 partition"，RocketMQ 是"写某个 topic 的某个 queue"。**只有 RabbitMQ 在中间插了一层 Exchange**。所以 RabbitMQ 的路由能力最强（一条消息可以扇出到 N 个队列），这也是它适合"业务解耦"的根本原因。

**认知 ②：Exchange 不存消息，路由不到就丢。**
这是新手第一大坑——发了一条消息，管理台里队列没动静，因为 binding 没配好。默认行为是**静默丢弃**。
两个解法：
- 生产端加 `mandatory=true` → 路由失败时 Broker 回一个 `basic.return`，你能感知到
- 配 **alternate-exchange（备份交换机）** → 路由不到的消息转到备份交换机，不丢

**认知 ③：消息 ack 后即删除，没有 offset，不能回溯。**
RabbitMQ 是"队列"语义（消费即消失），Kafka 是"日志"语义（按时间/大小保留，可重复消费）。这个差异会直接影响设计：**想做"重放历史消息"就不能用 RabbitMQ**。

## 1.3 一条消息的完整生命周期（背下来）

```
1. 生产者 publish 到 exchange，带 routingKey 和 properties
2. exchange 查 binding 表，匹配到 N 个 queue
3. 消息入队（若 queue 满/DLX 触发 → 走死信）
4. Broker 给生产者回 publisher confirm（若开启）
5. 消费者 basic.consume 或 basic.get 拿到消息（redelivered 标志可能为 true）
6. 消费者处理业务
7. 消费者 basic.ack → Broker 删除消息
   若 nack/reject 且 requeue=false → 进死信队列
   若消费者断连未 ack → 消息重回队列，redelivered=true
```

# 第 2 章 · 四种 Exchange（RabbitMQ 的独门能力）

| 类型 | 路由规则 | 典型场景 |
|---|---|---|
| **direct** | RoutingKey **完全相等**才投递 | 点对点精确投递，如按日志级别分流 `error` / `info` |
| **topic** | RoutingKey **通配符**匹配 | 最常用。`order.created`、`order.*.paid`、`order.#` |
| **fanout** | **忽略 RoutingKey**，投给所有绑定的队列 | 广播：缓存刷新、配置推送、多系统同步同一事件 |
| **headers** | 按消息 header 的键值匹配（`x-match: all/any`） | 复杂条件路由，**性能差，实际很少用** |

## topic 的通配符规则（必考细节）
- RoutingKey 用 `.` 分词，如 `order.cn.created`
- `*` 匹配**恰好一个词**：`order.*.created` 能匹配 `order.cn.created`，不能匹配 `order.created`
- `#` 匹配**零个或多个词**：`order.#` 能匹配 `order.created` 和 `order.cn.vip.created`

## 两个补充
- **默认交换机**：名字是空字符串 `""`，每个队列自动以队列名作为 RoutingKey 绑上去。所以 `channel.basicPublish("", "myQueue", ...)` 能直接发到名为 `myQueue` 的队列——这是"看起来生产者直发队列"的假象。
- **Exchange 也是要声明的**，且声明是幂等的（已存在且属性一致则无操作，属性不一致会报 `406 PRECONDITION_FAILED` 并关掉 channel——线上常见事故）。

# 第 3 章 · 消息的属性（可靠性的着力点）

RabbitMQ 的消息 = **properties（属性）+ body（消息体）**。面试里问可靠性，开关全在这些属性上：

| 属性 | 作用 | 可靠性意义 |
|---|---|---|
| `deliveryMode` | 1=非持久，2=持久 | **设 2 才可能落盘**（还要队列 durable） |
| `messageId` | 消息唯一 ID | 幂等键的候选（但推荐业务 ID） |
| `correlationId` | 关联 ID | RPC 模式里把请求和响应配对 |
| `replyTo` | 回调队列名 | RPC 模式 |
| `expiration` | 消息级 TTL（毫秒字符串） | 延迟队列 |
| `priority` | 优先级 0~9（或 0~255） | 需队列声明 `x-max-priority` |
| `headers` | 自定义键值 | 放业务 ID / traceId / 重试次数 |
| `timestamp` | 时间戳 | 排查 |
| `contentType` / `contentEncoding` | 序列化信息 | — |

**记住一句话**：`durable`（队列属性）和 `deliveryMode=2`（消息属性）是**两个独立的开关，必须同时打开**，只开一个都保证不了重启不丢。这是最高频的坑。

# 第 4 章 · 五大必考题（RabbitMQ 版）

## 4.1 怎么保证消息不丢 ★★★★★

**框架：三段链路，每段一个开关。缺一段就等于没做。**

### 第一段：生产者 → Broker

**① publisher confirm（主力方案）**
Broker 收到消息并**落到磁盘后**（持久化消息）回一个 ack。三种用法：

| 方式 | 写法 | 吞吐 | 场景 |
|---|---|---|---|
| 同步单条 | `waitForConfirms()` | 最低 | 极少数关键消息 |
| 批量同步 | 攒 100 条 `waitForConfirmsOrDie()` | 中 | 折中 |
| **异步回调** | `ConfirmListener.handleAck/handleNack` | **最高** | **生产推荐** |

关键理解：`ConfirmListener` 回调里有 `deliveryTag` 和 `multiple` 标志，`multiple=true` 表示"这个 tag 之前的所有消息都确认了"，可以批量清理待确认表。

**② 事务（txSelect / txCommit）**
能保证，但**性能下降非常明显**（同步阻塞 + fsync），生产基本不用。面试答"知道但不推荐，用 confirm 替代"就够。

**③ mandatory + basic.return**
解决"消息到了 Exchange 但路由不到 Queue 被静默丢弃"。`mandatory=true` 时，不可路由的消息会通过 `ReturnListener` 回来。**confirm 只保证 Broker 收到了，不保证路由成功了**——这个区别很多人答不出来。

**④ 失败重试 + 本地消息表兜底**
confirm 是 nack 或超时怎么办？重发；重发还失败就落本地表，定时任务补发。**这是"不丢"的最后一道防线。**

### 第二段：Broker 内部

| 开关 | 做法 | 说明 |
|---|---|---|
| 队列持久化 | `durable=true` | 队列元数据不丢 |
| 消息持久化 | `deliveryMode=2` | 消息体落盘 |
| **Quorum Queue** | `x-queue-type=quorum` | 基于 Raft 多副本（3 节点起），**这才是真正的高可用** |
| 镜像队列 | `ha-mode: all` | 老方案，3.9 标记废弃，**4.0 已移除**，别再说它 |
| 刷盘 | RabbitMQ 无"同步/异步刷盘"配置 | 持久化消息的 confirm 在落盘后发出（classic 队列批量 fsync） |

⚠️ **反直觉的点**：持久化 ≠ 立即 fsync 每条消息。RabbitMQ 会攒批刷盘，所以极端断电仍可能丢最后一批。要绝对可靠靠 **Quorum Queue 的多数派复制**，不靠单机刷盘。

### 第三段：Broker → 消费者

**① 关掉 autoAck，手动确认**
```java
// 错：autoAck=true，消息一到就删，处理失败就永久丢
channel.basicConsume(queue, true, callback);

// 对：处理成功后再 ack
channel.basicConsume(queue, false, new DefaultConsumer(channel) {
    public void handleDelivery(...) {
        try {
            doBusiness(body);              // 先干活
            channel.basicAck(tag, false);  // 干完再确认
        } catch (Exception e) {
            // requeue=false → 进死信；true 且不控制次数 → 死循环
            channel.basicNack(tag, false, false);
        }
    }
});
```

**② 失败处理的三条路**
- `basicNack(requeue=true)`：重回队列。危险——如果消息本身有问题（毒消息），会无限循环打爆 CPU。
- `basicNack(requeue=false)`：丢弃或进死信队列。**推荐**，配合 DLX + 人工/定时补偿。
- `basicReject`：只能拒绝单条（nack 支持 `multiple` 批量），功能上是 nack 的子集。

**③ prefetch（basic.qos）—— 别忽略它**
`prefetchCount` 限制"每个消费者最多有多少条未 ack 的消息"。
- 不设（默认 0 = 无限）→ 消费者被一次性推几万条，内存爆、OOM
- 设太小（如 1）→ 吞吐极低
- 经验：**从 100~300 起调**，看 consumer utilisation 指标

### 收尾话术
> "RabbitMQ 只能做到 at-least-once。生产端 confirm+return、Broker 端持久化+Quorum 多副本、消费端手动 ack 且先处理再确认，三段齐了才不丢。然后靠消费端幂等兜住重复。"

## 4.2 怎么保证不重复消费（幂等）★★★★★

**先承认现实**：RabbitMQ 必然重复。触发场景：
1. 消费者处理完业务，还没 ack 就宕机/网络断 → 消息重回队列
2. `requeue=true` 的 nack → 重新投递
3. 消费者 `prefetch` 拿到消息后连接被踢 → 所有未 ack 消息重投
4. **Quorum Queue 的 leader 切换** → 未确认消息重投
5. 生产者 confirm 超时但消息实际已入队 → 生产者重发 → 重复

### `redelivered` 标志能用来判重吗？
**不能，或只能作为辅助。**
- `true` 表示"这条消息之前投递过"，但**首次投递也可能因连接抖动被打上 true**
- 而真正的业务重复可能来自"生产者重发"，此时是全新消息，`redelivered=false`

所以判断重复**只能靠业务幂等键**。

### 幂等的五种实现（按推荐度）

| 方案 | 实现 | 优缺点 |
|---|---|---|
| **数据库唯一索引** ⭐ | `unique key (biz_type, biz_id)`，冲突就忽略 | 最可靠，数据库原子性保证，并发安全 |
| **去重表** | 处理前 insert `(msg_id)`，唯一冲突=重复 | 通用，但多一次写 |
| **状态机** ⭐ | `update order set status='PAID' where id=? and status='UNPAID'`，影响行数=0 就跳过 | 最优雅，天然幂等 |
| **Redis SETNX** | `setnx(biz_id, 1)` + 过期 | 快，但要处理"处理失败但 key 已写"，不能简单删 key |
| **乐观锁** | `where version=?` | 适合更新场景 |

### 幂等键放哪？
- 放 `messageId`：RabbitMQ 不会改写你设的 messageId，重投时保持一致，**技术上可用**
- 但更稳的是放 **headers 或 body 里的业务 ID**（订单号+业务类型）。原因：生产者可能忘设 messageId；同一业务动作可能发了多条消息，用 messageId 去重反而漏掉合法的第二条

**标准答法**：
> "用业务唯一键做幂等，落在数据库唯一索引上，把并发和重复一起解决。messageId 可以作为辅助，但不能作为唯一依据。"

## 4.3 怎么保证消息顺序 ★★★★

**RabbitMQ 的顺序保证弱，必须靠架构约束。**

### 唯一可靠的做法
```
单队列 + 单消费者 + prefetch=1
```
因为**一个队列一旦挂多个消费者，Broker 就轮询投递，并发消费必然乱序**。

### 但单队列单消费者吞吐太低，怎么办？→ 分区顺序
```
order.queue.0  ← 订单号 % 4 == 0 的消息   ← 消费者 A（单线程）
order.queue.1  ← 订单号 % 4 == 1 的消息   ← 消费者 B（单线程）
order.queue.2  ...
order.queue.3  ...
```
- 生产者自己算 hash 选队列（**不能靠 topic exchange 通配符，得自己算**）
- 每个队列**独占一个消费者、prefetch=1、单线程处理**
- 效果：**同一订单严格有序，不同订单并行**——这就是"局部有序"，也是业务真实需求

### 三个破坏顺序的坑（能说出这些就甩开大多数人）
1. **失败重试**：`requeue=true` 的消息重回队列，跑到后续消息后面 → 乱序。所以顺序场景**不能用 requeue 重试**，要用"失败落库 + 单线程按序补"
2. **多消费者**：最直接的破坏者
3. **多队列扇出**：一条消息投到多个队列，两个队列消费速度不同，最终结果可能乱（业务上要能接受）

### 死信也会乱序
nack 进死信队列后，人工补发回来的时间是"现在"，早就不是原来的顺序了。**顺序消息 + 死信是天然冲突的**，要单独设计补偿。

## 4.4 消息积压怎么办 ★★★★

**RabbitMQ 在这一项上是三家最弱的**，因为它有个硬限制：

> **一个队列的消费并行度受限于"一个队列能挂几个消费者"**，而队列扩容不像 Kafka 那样"改个分区数"就行。

### 第一步：先看指标（别瞎猜）
管理台 / API 看四个数：
- `messages_ready`：待消费堆积量
- `messages_unacknowledged`：已投递未确认（**大 = 消费者卡住或 prefetch 过大**）
- `publish rate` vs `deliver/ack rate`：进出是否失衡
- `consumer utilisation`：消费者利用率（低 = 消费者不够或 prefetch 太小）

### 第二步：定位原因
- 消费者进程挂了 / 一直在重连 → 看日志
- 消费变慢（下游 DB 慢、同步远程调用、GC）→ 看单条处理耗时
- 生产突增 → 看 publish rate 曲线
- **毒消息无限 requeue 循环** → unacked 不高但 CPU 打满，这是经典事故

### 第三步：扩容（按可行性排序）
1. **加消费者**（前提：队列数够）—— 但注意多消费者会破坏顺序
2. **多队列方案**：如果一开始就按业务分了多个队列，直接加消费者最有效
3. **临时转发程序**（队列不够时的标准答案）：
   ```
   写一个"搬运工"消费者，用最快的速度（autoAck + 不做业务）
   把积压队列的消息取出来，按 hash 转发到 8 个临时队列，
   再用 8 个消费者并行处理
   ```
   这是 RabbitMQ 积压的标准应急手段，**因为没有"扩分区"这个操作**。
4. **优化消费逻辑**（见效最快，常被忽略）
   - **批量 ack**：`basicAck(tag, multiple=true)`，一次确认一批
   - `prefetch` 从 100 调到 500~1000
   - 去掉消费逻辑里的同步 RPC，改批量查库 / 异步
5. **降级丢弃**：非核心消息（日志、埋点）设 `x-max-length` 或直接清队列，先保命

### 第四步：预防
- 监控 `messages_ready` 和 `messages_unacknowledged`，设阈值告警
- 队列设 `x-max-length` + `x-overflow: reject-publish`，防止无限堆积打爆磁盘
- 消费端限流 + 熔断，别让下游挂了反过来拖死队列
- 死信队列 + 定时巡检

⚠️ **致命坑**：队列无限增长 → 磁盘到 `disk_free_limit`（默认 50MB）→ **RabbitMQ 阻塞所有生产者连接**（`connection.blocked`）→ 整个系统写不进去。这个连锁反应是真实事故。

## 4.5 RabbitMQ 自己的高可用 ★★★★

### 三种集群形态（必须能讲清区别）

**① 普通集群（Classic Cluster）**
- Exchange、Binding、Queue 的**元数据**同步到所有节点
- **队列的消息数据只存在声明它的那个节点**
- 消费者连到别的节点，Broker 会内部转发 → 有额外开销
- ⚠️ **那个节点挂了，这个队列的数据就没了** → 不是真正的高可用

**② 镜像队列（Mirrored Queue）—— 已淘汰，别说它是首选**
- 队列复制到多个节点，一主多从，主挂从顶上
- 缺点：**同步复制开销大**，网络和磁盘压力翻倍，队列越多越慢；网络分区时容易脑裂
- **3.9 标记废弃，4.0 已移除**。面试时说"这是老方案，现在用 Quorum Queue"是加分项

**③ Quorum Queue（推荐，3.8+）**
- 基于 **Raft** 一致性协议复制，**多数派写入成功才 ack**
- 3 节点容忍 1 个故障，5 节点容忍 2 个
- 自动选主，无脑裂问题
- 限制：**不支持优先级队列、不支持 exclusive 队列、不支持非持久化**，且要求集群至少 3 节点
- 声明方式：`x-queue-type: quorum`

### 网络分区（network partition）
集群节点间心跳断了但都还活着 → 脑裂。三种处理策略：
- `pause_minority`：少数派节点自动暂停（**RabbitMQ 推荐**，保证一致性）
- `autoheal`：分区恢复后自动选一个赢家，丢弃另一边的状态
- `ignore`：不处理，需人工介入（最危险）

### 跨机房
用 **Federation**（联邦，双向同步，适合松耦合）或 **Shovel**（铲子，单向搬运，适合迁移/容灾）。

# 第 5 章 · 四个特有武器（RabbitMQ 面试的差异化得分点）

## 5.1 死信队列 DLX

**消息变死信的三个触发条件（必背）**：
1. 消费者 `basicReject` / `basicNack` 且 **`requeue=false`**
2. 消息 **TTL 过期**
3. 队列**达到长度/字节上限**被丢弃（`x-max-length` / `x-max-length-bytes`）

**声明方式**：
```java
Map<String, Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "dlx.exchange");
args.put("x-dead-letter-routing-key", "dlx.order");
channel.queueDeclare("order.queue", true, false, false, args);
```

**价值**：① 防毒消息无限重试堵死队列 ② 保留现场便于排查 ③ 人工/程序补偿的入口
**注意**：死信队列也需要消费者，否则死信越积越多，最后还是磁盘满。

## 5.2 TTL 与那个著名的坑

两种设 TTL 的方式：
- **队列级**：`x-message-ttl`，整个队列统一
- **消息级**：`expiration` 属性，每条不同

**⚠️ 队头阻塞（Head-of-Line Blocking）**：
RabbitMQ **只在消息到达队头时才检查是否过期**。如果队列里依次是 `TTL=30min`、`TTL=1min`，那条 1 分钟的消息要等 30 分钟那条过期了才能被判定过期。
→ **同一队列里 TTL 必须一致**，要不同延迟就建多个队列。

## 5.3 延迟消息（订单超时取消的标配题）

### 方案 A：TTL + DLX（经典，但有坑）
```
业务队列（x-message-ttl=30min, x-dead-letter-exchange=delay.dlx）
      ↓ 30 分钟后过期
死信交换机 → 真正的处理队列 → 消费者执行"取消订单"
```
**坑**：受上面队头阻塞限制 + 精度差（过期后才进死信，再被消费）+ 大量延迟消息占用内存

### 方案 B：rabbitmq_delayed_message_exchange 插件（推荐）
- 声明一个 `x-delayed-type` 的 Exchange，消息带 `x-delay` header（毫秒）
- 内部用 **Erlang 时间轮（timer wheel）** 实现，支持**每条消息不同延迟**
- 优点：精确、灵活；缺点：需装插件、延迟消息数受限于内存、官方不承诺极高量级

### 方案 C：兜底扫表（生产必备）
不管用哪个方案，**都要加定时任务扫订单表**："超时 30 分钟且状态仍为待支付 → 取消"。因为 MQ 挂了、插件丢了、消息被误删，定时任务还在。**双保险是标准工程实践。**

## 5.4 流控（Flow Control）

**两个水位**：
- `vm_memory_high_watermark`：内存水位，默认 0.4（占物理内存 40%）
- `disk_free_limit`：磁盘剩余，默认 50MB

**触发后发生什么？**
- 先**阻塞生产者连接**（通过 `connection.blocked` 通知客户端），**不丢消息**
- 内存继续涨 → 开始把消息**换出到磁盘**（paging）
- 极端情况 → 阻塞所有发布

**加分点**：RabbitMQ 的流控是"**推回压力给生产端**"，这是比"丢消息"优雅的设计。但代价是生产端会卡住，所以生产端要处理 `connection.blocked` 回调做降级。

# 第 6 章 · 把知识串起来：一个完整设计

**题目：电商订单 30 分钟未支付自动取消，要求不丢、不重、可补偿。**

```
【生产端】订单服务
  1. 本地事务：写 order 表（status=UNPAID）+ 写 msg_log 表（status=待发送）
     ← 同一个数据库事务，保证"订单和"要发的消息"原子
  2. 事务提交后，发消息到 delay.exchange（delayed-message 插件，x-delay=30min）
     开 confirm，ConfirmListener 收到 ack → msg_log 置为"已发送"
  3. 定时任务扫 msg_log 里"待发送"超过 1 分钟的记录 → 补发
     ← 这一层兜住 confirm 超时、进程崩溃

【Broker】
  4. delay 队列用 Quorum Queue（3 副本，Raft）+ 持久化
     ← 主节点挂了消息不丢

【消费端】订单服务（或独立的订单关闭服务）
  5. autoAck=false，prefetch=100，收到消息后：
     a. 幂等：update order set status='CANCELLED'
              where order_no=? and status='UNPAID'
        ← 影响行数 0 说明已处理过，直接 ack 返回
     b. 回滚库存：调库存服务，库存服务自己也要幂等（用 order_no 做幂等键）
     c. 全部成功 → basicAck
        失败 → basicNack(requeue=false) → 进死信
  6. 死信队列有消费者：落 cancel_fail 表 + 告警，人工/定时补偿

【兜底】
  7. 定时任务每 5 分钟扫 order 表：status=UNPAID 且 create_time < now-30min
     → 走取消流程（和消息消费调同一个幂等方法）
     ← MQ 全挂也能保证业务最终正确
```

**这段设计的考点全覆盖**：confirm（不丢）+ 持久化/Quorum（不丢）+ 手动 ack（不丢）+ 唯一条件更新（幂等）+ 死信（兜底）+ 扫表（最终一致）+ 延迟消息（定时）。

面试时能把这张图讲出来，比背十道题都有用。

# 第 7 章 · 七个高频追问 + 三个致命坑

### 追问

**Q1：confirm 收到 ack，就代表消费者消费成功了吗？**
> 不代表。confirm 只表示 **Broker 接收并持久化**成功，跟消费端完全无关。消费成功要靠消费端自己的 ack。

**Q2：消息发到 Exchange 了，但队列没收到，怎么回事？**
> 路由失败被静默丢弃。检查 binding 和 routingKey 是否匹配；生产端开 `mandatory=true` 接 `basic.return`，或配 alternate-exchange。

**Q3：消费者处理到一半进程被 kill，消息会丢吗？**
> 不会丢，会重投（`redelivered=true`），所以会**重复**。这正是必须做幂等的原因。

**Q4：消费者 ack 之后立刻宕机，会怎样？**
> 消息已删，业务已处理完，**没有影响**。所以 ack 必须放在业务处理之后——顺序反了就是"消息丢了但业务没做"。

**Q5：一个队列能挂多少个消费者？**
> 理论上不限，但**超过队列并行能力就是浪费**，且会破坏顺序。RabbitMQ 里消费者数量与队列数是 1:N 关系，扩容靠"加队列"而不是"加消费者"。

**Q6：怎么知道消费者消费不过来了？**
> 看 `messages_ready` 持续上涨、`consumer utilisation` 接近 100%（说明消费者一直满负荷）、`deliver rate` < `publish rate`。

**Q7：RabbitMQ 为什么吞吐比 Kafka 低？**
> ① 每条消息独立投递和确认，没有 Kafka 那种批量+offset 机制；② Erlang 进程模型虽然轻量，但消息要经过 Exchange 路由匹配、多次内存拷贝；③ 支持复杂的 per-message ack 和路由，功能换性能。它的优势是**低延迟和灵活路由**，不是吞吐。

### 三个致命坑（说出来就显专业）

**坑 1：durable=true 但 deliveryMode=1**
队列重启后还在，但里面的消息全没了。**两个开关必须同时开。**

**坑 2：autoAck=true**
看起来"消费很快"，实际上是"消息一投递就删"。消费者只要处理失败一次，消息就永久丢失。**这是线上最隐蔽的数据丢失源。**

**坑 3：requeue=true 配毒消息**
一条必然处理失败的消息，nack 后重回队列，又被投递、又失败……CPU 打满、日志刷爆、队列永远消费不完。**必须限制重试次数（靠 headers 记重试数）或直接 requeue=false 进死信。**

# 第 9 章 · 速记卡（考前 10 分钟）

```
模型：Producer → Connection → Channel → Exchange --Binding/RoutingKey--> Queue → Consumer
      三个铁律：① 生产者只发 Exchange ② Exchange 不存消息，路由不到就丢 ③ ack 后即删不可回溯

四种 Exchange：direct(全等) / topic(*一个词 #多个词) / fanout(广播) / headers(少用)

不丢三段：
  生产端  confirm(异步ConfirmListener) + mandatory/return + 重试 + 本地消息表
  Broker  durable=true 且 deliveryMode=2（两个都要！）+ Quorum Queue
  消费端  autoAck=false + 先处理再 basicAck + prefetch 限量

不重：at-least-once 必然重复 → 幂等（唯一索引/状态机/去重表/Redis）
      幂等键用业务ID，别只靠 messageId 和 redelivered

有序：单队列单消费者 prefetch=1 → 吞吐低 → 分区顺序(按业务key hash 到 N 个队列，各一个消费者)
      三个破坏者：多消费者 / requeue 重试 / 死信补发

积压：看 messages_ready + unacked + consumer utilisation
      扩容受"队列数"限制，不能像 Kafka 扩分区
      应急：临时转发程序搬到多队列 / 批量 ack / 调大 prefetch / 限流丢弃
      致命：磁盘到 disk_free_limit → 阻塞所有生产者

高可用：普通集群(元数据同步，队列数据单点) → 镜像队列(已废弃/4.0移除) → Quorum Queue(Raft，推荐)
       网络分区策略：pause_minority > autoheal > ignore
       跨机房：Federation / Shovel

死信三触发：reject/nack 且 requeue=false ｜ TTL 过期 ｜ 超长超字节
TTL 坑：只在队头检查 → 同队列 TTL 必须一致
延迟：TTL+DLX(有坑) / delayed-message-exchange 插件(时间轮) / 必须加扫表兜底
流控：内存 40% + 磁盘 50MB → 阻塞生产者(connection.blocked)，不丢消息
```
