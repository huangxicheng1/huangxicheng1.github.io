这个问题分三层才答得清楚：**先分清是哪一种线程池 → 再讲生产上怎么用 → 最后讲怎么定容和调整**。很多人一上来就背「N+1、2N」，其实那只是第二层的一小部分。

---

## 一、先分清三类线程池，别混为一谈

生产上你其实同时在管三种池，职责完全不同：

| 类型 | 谁创建 | 决定什么 | 能不能动态调 |
|---|---|---|---|
| **容器线程池**（Tomcat） | Web 容器 | 能同时接住多少 HTTP 请求 | 能（`setMaxThreads`） |
| **RPC 线程池**（Dubbo） | 框架 | 能同时处理多少下游调用 | 能（配置中心 + `setCorePoolSize`） |
| **业务线程池**（自建） | 你自己 | 异步任务/并行编排的并发度 | 能（但队列容量默认不能） |

**关键认知**：这三层是**串联**的。Tomcat 200 线程 → 每请求打 1 次 DB + 2 次 RPC，那么 DB 连接池 20、RPC 池 200 就是真正的瓶颈。**线程池不是越大越好，它是「并发放大器」，会把压力一比一放大到下游。**

## 二、生产上怎么用：七条工程规范

这些是「会不会写生产代码」的分水岭，面试官很爱问「你们线程池怎么创建的」。

### 1. 禁止用 `Executors`，必须手写 `ThreadPoolExecutor`

`newFixedThreadPool` / `newSingleThreadExecutor` 用的是**无界队列**（`LinkedBlockingQueue` 默认 `Integer.MAX_VALUE`），任务堆积到 OOM，这是《阿里巴巴 Java 开发手册》第一条强制规约。

### 2. 必须命名线程

```java
ThreadFactory tf = new ThreadFactoryBuilder()
    .setNameFormat("order-query-pool-%d")
    .setUncaughtExceptionHandler((t, e) -> log.error("pool err", e))
    .build();
```

不命名的后果：线上 `jstack` 全是 `pool-1-thread-37`，根本不知道是哪个业务打满的。

### 3. 必须按业务/依赖隔离，不要全局一个池

```
order-core-pool      // 核心下单链路
order-async-pool     // 发短信、加积分（可丢）
report-pool          // 报表导出（慢，绝不能和核心共用）
```

**为什么要隔离**：报表任务把池占满 → 下单链路拿不到线程 → 整个站点雪崩。这就是微服务里「舱壁模式」在线程池层的体现。反过来，如果所有业务共用一个池，一个慢接口就能拖垮全站。

### 4. 必须有界队列 + 明确的拒绝策略

```java
new ThreadPoolExecutor(
    8, 16,
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),          // 有界！
    tf,
    new ThreadPoolExecutor.CallerRunsPolicy() // 反压
);
```

拒绝策略选择：

| 策略 | 适用 |
|---|---|
| `CallerRunsPolicy` | 推荐，让调用方自己跑，天然反压，自动降速 |
| `AbortPolicy` | 核心链路，抛异常让上层快速失败 + 告警 |
| 自定义 | 记录日志/打点 + 降级返回兜底值（最常用在真实项目） |
| `DiscardPolicy` | **慎用**，静默丢任务是排查噩梦 |

### 5. 上下文传递要显式处理

线程池复用线程会带来两个坑：

- **ThreadLocal 串数据/泄漏**：任务结束必须 `finally { tl.remove(); }`；跨线程传递用阿里 **TransmittableThreadLocal（TTL）**，`InheritableThreadLocal` 只在创建线程时复制一次，池化场景无效。
- **MDC / traceId 丢失**：日志里没有链路 ID，排查直接瞎。用 TTL 或 `TaskDecorator` 包装。

```java
// Spring 里最干净的写法
executor.setTaskDecorator(runnable -> {
    Map<String,String> ctx = MDC.getCopyOfContextMap();
    return () -> {
        if (ctx != null) MDC.setContextMap(ctx);
        try { runnable.run(); } finally { MDC.clear(); }
    };
});
```

### 6. 必须优雅关闭

```java
executor.shutdown();                                  // 拒绝新任务
if (!executor.awaitTermination(30, TimeUnit.SECONDS)) // 等在途任务
    executor.shutdownNow();                           // 中断
```

发布时直接杀进程 → 在途任务丢失（比如订单状态只写了一半）。Spring 环境下实现 `DisposableBean` 或 `SmartLifecycle`。

### 7. 必须可观测

至少暴露这几个指标到 Prometheus/Micrometer：

```
active_count, pool_size, queue_size, queue_remaining_capacity,
completed_task_count, rejected_count（需自定义计数）
```

没有 `rejected_count` 就等于不知道自己在丢任务。

## 三、参数怎么设：从公式到压测

### 第一步：判断任务类型

| 类型 | 特征 | 公式 |
|---|---|---|
| **CPU 密集** | 计算/加解密/序列化/图片处理 | `N + 1`（N = 核数，+1 防偶发缺页停顿） |
| **IO 密集** | 调 RPC、查 DB、读文件 | `N × (1 + 等待时间/计算时间)`，经验值 `2N` |
| **混合** | 又算又等 | **拆成两个池**，别硬算 |

IO 密集的公式含义很直观：**线程大部分时间在等，那就多给几个**。等待占比 90%（WT/ST=9），8 核 → 8×10 = 80 线程。

### 第二步：用 Little's Law 交叉校验

```
线程数 ≈ QPS × 单任务耗时(秒) × 冗余系数(1.5~2)
```

例：某异步任务 500 QPS、单任务 100ms → 500×0.1 = 50 → 设 75~100。

**如果公式算出来比 `N+1` / `2N` 大很多**，说明你的任务耗时太长（慢 SQL、同步 RPC），**应该先优化任务本身，而不是加线程**——这一点面试时说出来很加分。

### 第三步：队列长度怎么定

这是最容易被忽略的参数。原则：

```
队列长度 ≈ 可容忍的排队时间 × QPS
```

例：QPS 500，用户可接受 2 秒内完成，单任务 100ms → 队列最多积压 20 个任务就该失败。你设 10000 的队列，任务在队列里躺 20 秒才被执行，**用户早就超时了，这个任务执行了也是白执行，还占内存**。

**所以：短队列 + 快速失败 > 长队列 + 延迟堆积。** 这和 Dubbo `queues=0` 是同一个思想。

### 第四步：压测找拐点（不能只信公式）

固定 QPS，逐步调大线程数，观察：

| 现象 | 结论 |
|---|---|
| QPS 随线程数线性上升，RT 平稳 | 还没到拐点，可继续加 |
| QPS 不再涨，RT 开始上升 | **饱和点，就是这里** |
| QPS 下降，RT 陡增，CPU `sy` 飙高 | 超过拐点，上下文切换在吃 CPU |

**拐点位置 = 你的线程数上限**。公式只是起点，压测才是终点。

## 四、怎么根据实际情况调整（这才是生产重点）

### 4.1 先看指标组合，别单看一个数

这是判断的核心方法，五个指标组合能定位 90% 的问题：

| active | queue | rejected | 说明 | 该怎么调 |
|---|---|---|---|---|
| 低 | 空 | 0 | 池太大，浪费资源 | **调小**，或缩短 keepAlive |
| 高 | 空 | 0 | 线程都在干活，没积压 | 看是不是下游慢（线程卡在 socketRead）；真不慢才加线程 |
| 高 | 涨 | 0 | 处理能力不足 | 先看下游能否承受，再考虑加线程/加机器 |
| 高 | 满 | >0 | **已经出事了** | 立即：限流 + 降级；事后：定位慢任务 |
| 低 | 涨 | 0 | 诡异：线程空闲但任务排队 | 检查是不是 `core=max` + 队列优先导致不扩容（见下方坑 3） |

### 4.2 一个必须知道的坑：扩容顺序错了就不会扩容

`ThreadPoolExecutor` 的执行流程是「核心满 → 入队列 → 队列满 → 扩到 max」。

所以如果你设 `core=8, max=64, queue=1000`，**运行中永远只有 8 个线程在跑**，因为队列几乎不可能满，`max=64` 形同虚设。

正确做法二选一：
- 要弹性 → **队列设小**（如 100），让队列快速打满触发扩容
- 要稳定 → `core = max`，用队列做缓冲，靠 CallerRuns 反压

### 4.3 动态调整怎么做

`ThreadPoolExecutor` 的 `setCorePoolSize` / `setMaximumPoolSize` 是**运行时可用**的，这就是动态线程池的基础。

**标准做法（美团动态线程池那套）**：

```
配置中心（Nacos/Apollo）→ 监听变更 → 校验参数 → 调整 → 上报生效结果
```

三个必须处理的细节：

**① 调整顺序，否则抛异常**（`core > max` 会 `IllegalArgumentException`）

```java
// 调大：先 max 后 core
executor.setMaximumPoolSize(newMax);
executor.setCorePoolSize(newCore);

// 调小：先 core 后 max
executor.setCorePoolSize(newCore);
executor.setMaximumPoolSize(newMax);
```

**② 队列容量默认改不了** —— `ArrayBlockingQueue` 的 capacity 是 final 的。美团的做法是实现一个 `ResizableCapacityLinkedBlockingQueue`，用 volatile 的 capacity 字段 + 重写 `offer/put` 判断。

**③ 调小不会立刻生效** —— 调小 core 后，多出来的线程要等空闲超过 `keepAliveTime` 才回收；想立即生效可以用 `allowCoreThreadTimeOut(true)` 或主动 `interrupt` 空闲线程（不推荐，风险大）。

**④ 调大也不一定立刻建线程** —— 除非调用 `prestartAllCoreThreads()` 或 `prestartCoreThread()`。

### 4.4 容器线程池（Tomcat）怎么动态调

Tomcat 的 `maxThreads` 运行时可改，但要注意**不能小于当前活跃线程数**：

```java
@Component
public class TomcatThreadPoolCustomizer
        implements WebServerFactoryCustomizer<TomcatServletWebServerFactory> {

    @Override
    public void customize(TomcatServletWebServerFactory factory) {
        factory.addConnectorCustomizers(connector -> {
            ProtocolHandler handler = connector.getProtocolHandler();
            if (handler instanceof AbstractProtocol<?> p) {
                p.setMaxThreads(300);
                p.setAcceptCount(200);
                p.setMaxConnections(10000);
            }
        });
    }
}
```

运行期通过拿到 `AbstractProtocol` 引用直接 `setMaxThreads()` 即可（Spring Boot 3 用 `WebServerApplicationContext.getWebServer()`）。

**但更重要的是**：Tomcat 线程数受制于下游。DB 连接池 20，你把 Tomcat 调到 500，结果只是 500 个线程排队等 20 个连接 —— **排队位置从 Tomcat 转移到了连接池，RT 一样难看**。这两者要**匹配着调**。

## 五、四个真实事故模式（面试讲这个非常有料）

**① 无界队列 OOM**
报表导出任务突发涌入，`LinkedBlockingQueue` 堆了几十万个任务对象 → `OutOfMemoryError: Java heap space`。
→ 改有界队列 + 拒绝策略 + 前置限流。

**② 父子任务共用线程池死锁**
主任务提交子任务到同一个池并 `future.get()` 等结果。池被主任务占满，子任务永远排不上 → 全部线程 WAITING，池彻底卡死。
→ 用不同的池（父子隔离），或用 `ForkJoinPool`（work-stealing 会帮忙）。

**③ core<max + 大队列，max 永不生效**
如 4.2 所述，压力测试时发现「线程数永远是 8，但 RT 很高」，查半天以为是下游问题。
→ 队列改小，或 core=max。

**④ 拒绝策略静默丢弃导致数据丢失**
`DiscardPolicy` + 没有 `rejected_count` 监控 → 大促期间丢了 3 万条积分消息，一周后对账才发现。
→ 换 CallerRuns 或自定义策略，拒绝必须打日志 + 打点 + 告警。

## 六、完整闭环（面试收尾用）

```
定容：任务类型公式（N+1 / 2N）→ Little's Law 校验 → 压测找拐点
配置：有界队列（≈ 可容忍排队时间 × QPS）+ CallerRuns + 命名 + 隔离
上线：暴露 active/queue/rejected/acquire 指标 + 告警阈值
调整：看指标组合定位 → 配置中心推送 → 注意调整顺序与队列容量 → 灰度验证
兜底：前置限流 + 降级 + 优雅关闭
```

## 30 秒话术

> 「生产上我先按来源分清三类池：Tomcat 容器池、Dubbo RPC 池、业务自建池，它们是串联的，线程池本质是并发放大器，会把压力放大到下游，所以要和连接池匹配着调。业务池我一定手写 ThreadPoolExecutor，不用 Executors，因为有界队列、线程命名、业务隔离、CallerRuns 反压这四件事必须自己控。参数上先按任务类型算，CPU 密集 N+1、IO 密集 2N 或用 N×(1+WT/ST)，再用 QPS×RT 校验，最后靠压测找拐点。队列长度按‘可容忍排队时间×QPS’定，宁可短队列快速失败，也不要长队列延迟堆积。运行期看 active、queue、rejected 三个指标的组合判断，动态调整走配置中心，注意调大要先改 max 后改 core、调小反过来，而且队列容量默认是不可变的，需要自定义可伸缩队列。最后配前置限流和降级兜底。」

---

一句话记住：**线程池解决的是「并发编排」，不是「性能提升」**。池子大小的上限，永远由它下游最慢的那一环决定。
