## 2. A 部分逐单元详解

### A1 主从延迟

① 结论：延迟判据只认外部心跳表，Seconds_Behind_Master 只能当粗筛。

② 为什么：SBM 的口径是 relay log 中已执行事件的头部时间戳与从库当前时钟之差，从库时钟回拨会直接污染该值；多线程复制下该值取已应用事务推进位置的最小值，因此大事务提交时会出现阶梯跳变与瞬时归零；SBM 不反映 IO 线程拉取进度，主库 binlog 已产生而从库尚未拉取的部分不计入；GTID 多级拓扑下中间节点的 SBM 无法代表末端节点真实滞后；半同步的确认点在 after_sync 模式下位于引擎提交之后、应答之前，该等待与复制延迟在监控上会混为同一指标。

③ 判据：心跳表（percona.heartbeat）在从库的 TS 差值连续 3 个采样点超过 1s（同机房）或超过 5s（跨机房）判定为延迟。
```bash
pt-heartbeat --host=主库 --update --interval=1 --database=percona --create-table
pt-heartbeat --host=从库 --monitor --interval=1
```
辅助判据是 GTID 缺口量化：
```sql
SELECT GTID_SUBTRACT(@@global.gtid_executed, '已执行集合') ;
SHOW REPLICA STATUS\G
```
输出中看 Retrieved_Gtid_Set 与 Executed_Gtid_Set 的差集条数，差值持续扩大即为拉取或应用瓶颈。

③ 止血：动作是把一致性敏感的读流量切回主库，代价是主库 QPS 抬升，回滚方式是路由权重回切。批量导入类写入直接暂停，代价是可接受的业务延迟，回滚方式是恢复任务队列。

③ 根因：三个入口是从库 worker 状态、主库写入特征、从库资源。
```sql
SELECT WORKER_ID, APPLYING_TRANSACTION, LAST_APPLIED_TRANSACTION,
       APPLYING_TRANSACTION_IMMEDIATE_COMMIT_TIMESTAMP
FROM performance_schema.replication_applier_status_by_worker;
SHOW GLOBAL VARIABLES LIKE 'replica_parallel_workers';
```
互证方式是 worker 中仅单线程繁忙且主库同时段存在大事务，即可排除网络因素；若所有 worker 均空闲而延迟仍涨，则指向 IO 线程或网络。

③ 治理：版本层用 8.0 的 WRITESET 依赖追踪（binlog_transaction_dependency_tracking）；参数层 replica_parallel_workers 提到 8 至 16 并保持 replica_preserve_commit_order=ON；代码层单事务影响行数控制在 1 万以内、单事务时长控制在 100ms 内；架构层核心读走主库或强一致读接口。验收口径是心跳表 P99 延迟低于 500ms 且连续 7 天无尖峰。
方案取舍：提高并行度见效分钟级、回滚成本为零、代价是内存与提交顺序约束；拆大事务见效天级、回滚成本中等、代价是业务改造。

④ 延伸与边界：失效条件一是单线程复制（5.7 默认 slave_parallel_workers=0），此时并行度调参无效，现象是延迟只随写入串行线性增长。失效条件二是所有写入集中单库，库级并行退化为串行，现象是 worker 全忙但只有一个 worker 有事务。失效条件三是延迟从库（SOURCE_DELAY）场景，SBM 为负值属预期而非故障。更深机制点是并行复制的冲突判定依赖主库写入时生成的行级 hash 集合，冲突检测粒度是行而非表，因此热点行的写入天然串行。相邻场景差异是半同步等待超时降级为异步，此时代理层看到的延迟正常而数据实际已滞后，A1 的判据在此处失效。

⑤ 常见误述与校准：说法「SBM 为 0 即无延迟」不成立，因为该值取自事件时间戳而非数据可见性，长事务提交期间恒为小值；正确表述是延迟以心跳表差值为准。说法「加从库能缓解延迟」不成立，因为从库数量不改变单从库的应用吞吐；正确表述是延迟由单从库应用速度决定。说法「延迟都是网络问题」不成立，因为多数延迟来自大事务与单线程应用；正确表述是先看 worker 忙闲再判网络。

⑥ 抓手：有心跳差值才叫有延迟。

### A2 主从切换与脑裂

① 结论：脑裂阻断靠只读约束加仲裁单点，VIP 漂移只是流量表象。

② 为什么：VIP 的归属由外部机制决定，旧主在失联期间仍可接受本地连接，因此出现双写的时间窗等于探测超时；read_only 只拦截普通用户的写，具备 SUPER 权限的账号与复制线程不受限，super_read_only 才覆盖超级用户；切换后新主的 GTID 集合若未包含旧主最后一秒事务，回补必须以 GTID 差集为单位而非以时间点为界；主库 crash 后 relay log 可能残留未应用事务，反向补数据时该部分会重复；半同步在 after_sync 下才保证应答前已落从库 relay log，after_commit 存在丢事务窗口。

③ 判据：两侧 gtid_executed 存在互不包含的事务即判定分叉。
```sql
SELECT @@global.gtid_executed;
SELECT GTID_SUBTRACT('集合A','集合B');
```
切换后 30s 内两侧均出现写入（Threads_running 与 Com_insert 同时非零）判定为双写。

③ 止血：动作是对旧主执行 SET GLOBAL super_read_only=ON 并 KILL 其业务连接，代价是旧主业务中断，回滚方式是解除只读并重建复制。
```sql
SET GLOBAL super_read_only=ON;
FLUSH TABLES WITH READ LOCK;  -- 仅备份窗口使用，会阻塞写入
SELECT id, user, host, command FROM information_schema.processlist WHERE command <> 'Sleep';
```
切换期先执行 SET GLOBAL read_only=ON 再变更 VIP，顺序不可颠倒。

③ 根因：三个入口是 binlog 事件比对、中间件路由日志、VIP 归属记录。互证方式是以两侧 binlog 的 server_id 与 end_log_pos 对齐，若同一 GTID 在两侧内容不同（用 mysqlbinlog 解码比对）则可确认分叉而非重复。

③ 治理：版本层用 8.0 的组复制或带一致性协议的编排器；参数层固定 server_id 与 gtid_mode=ON、enforce_gtid_consistency=ON；代码层禁止跨库写入绕过统一入口；架构层加仲裁节点与 fencing 脚本，网络分区时以仲裁结果单边只读。验收口径是每年两次切换演练，双写窗口为 0，数据差异行数为 0。
方案取舍：编排器自动切换生效秒级、回滚需人工确认、风险是误判；人工切换生效分钟级、回滚成本低、风险是响应慢。

④ 延伸与边界：失效条件一是旧主所在网络完全隔离但主机存活，super_read_only 无法远程下发，现象是隔离侧持续写入。失效条件二是中间件缓存了连接映射，只读下发后旧连接仍在写，现象是只读生效但 Com_insert 不降。更深机制点是 GTID 的自动跳过依赖事务编号连续性，跨主补数据产生的新事务会改变后续编号映射，因此回补必须在注入前记录边界。相邻场景差异是 A8 误删恢复同样用 binlog 回放，但方向相反，A2 的回补以补齐缺失事务为目标，不做反向撤销。

⑤ 常见误述与校准：说法「VIP 切走即无脑裂」不成立，因为旧主仍可被直连；正确表述是只读与网络双重约束才终止写入。说法「read_only 足以防写」不成立，因为超级用户绕过；正确表述是用 super_read_only。说法「切换后比对行数足够」不成立，因为行数相同不代表内容相同；正确表述是用 pt-table-checksum 做块级校验。

⑥ 抓手：先单边只读，再谈数据补齐。

### A3 死锁（1213）

① 结论：死锁是等待图成环后的主动回滚，处置主线是统一加锁顺序。

② 为什么：InnoDB 以事务为节点、以锁等待为有向边构建等待图，检测到环即回滚代价较小的一方（按事务持有与修改的行数估算）；间隙锁（Gap Lock）在可重复读下封锁区间，两个不同条件的范围更新会因插入意向锁与间隙锁互斥而成环；唯一键冲突时的共享锁升级会形成 S 锁与 X 锁交叉等待；死锁检测由 innodb_deadlock_detect 控制，关闭后降级为超时回滚；死锁回滚不释放已写入的 undo，回滚本身仍需时间，因此高并发下死锁会放大为锁等待队列。

③ 判据：应用侧收到 1213，且错误日志或状态输出中存在等待环。
```sql
SHOW ENGINE INNODB STATUS\G   -- 看 LATEST DETECTED DEADLOCK 段
SET GLOBAL innodb_print_all_deadlocks=ON;  -- 8.0 全量落错误日志
```
8.0 用 performance_schema.data_locks 与 data_lock_waits 复现锁结构，5.7 对应 information_schema.innodb_lock_waits。判定阈值：同一表在 10 分钟内出现 3 次以上死锁，视为结构性问题。

③ 止血：动作是回滚业务侧受影响事务并重试，代价是少量请求失败，回滚方式是重试幂等。热点表短时降并发，代价是吞吐下降。
```sql
SELECT * FROM performance_schema.data_lock_waits\G
SELECT trx_id, trx_state, trx_started, trx_rows_locked FROM information_schema.innodb_trx;
```

③ 根因：三个入口是死锁段的事务 SQL 文本、两侧事务的加锁顺序、执行计划是否走了预期索引。互证方式是若两条 SQL 的 WHERE 条件不同但加锁区间重叠，则根因是范围扫描扩大而非业务并发。未命中索引导致的锁范围扩大，可用 EXPLAIN 中 rows 与 type 验证。

③ 治理：版本层升级到 8.0 以获得更完整的锁视图；参数层保留 innodb_deadlock_detect=ON，innodb_lock_wait_timeout 按业务重试预算下调到 10 至 20s；代码层统一按主键升序批量更新；架构层把跨表更新收敛到单一服务。验收口径是死锁次数按周下降且 P99 无锁等待尖峰。
方案取舍：统一加锁顺序改造周期长、回滚成本高、收益彻底；提高重试次数见效快、回滚容易、代价是放大锁竞争。

④ 延伸与边界：失效条件一是关闭死锁检测（innodb_deadlock_detect=OFF）后，现象由 1213 变为 1205 超时，等待时间被拉长到 innodb_lock_wait_timeout。失效条件二是 RC 隔离级别下间隙锁消失，同样的 SQL 不再成环，但会出现幻读与更多行锁。更深机制点是插入意向锁与间隙锁的兼容矩阵决定了 INSERT 在范围锁下的排队行为，因此二级唯一索引冲突比主键冲突更容易死锁。相邻场景差异是 A4 的锁等待超时无环，处置手段是终止长事务而非调整顺序，两类的判据不可互换。

⑤ 常见误述与校准：说法「死锁是数据库缺陷」不成立，因为环由业务加锁顺序造成；正确表述是死锁是并发控制的正常输出。说法「重试即可解决」不成立，因为重试在相同顺序下会重复成环；正确表述是重试配合顺序统一才有效。说法「死锁一定伴随慢查询」不成立，因为死锁发生在毫秒级；正确表述是死锁看次数，慢查询看耗时。

⑥ 抓手：环由顺序生，顺序定则环消。

### A4 锁等待超时（1205）与长事务

① 结论：1205 是无环的等待超时，根因定位以持锁时长为主轴。

② 为什么：行锁等待在 innodb_lock_wait_timeout 到期后抛出 1205 并回滚当前语句，事务本身可能仍存活；长事务不提交会持续持有行锁与 undo，同时阻塞 purge 线程，历史版本链膨胀会拖慢后续读；元数据锁（MDL）由 lock_wait_timeout 控制，默认极大，因此 DDL 会被长事务无限期挡住；只读事务在 RC 下也会因一致性读持有短暂的元数据锁。

③ 判据：错误码 1205，且 information_schema.innodb_trx 中存在 trx_started 早于当前时间 60s 的事务。
```sql
SELECT trx_id, trx_state, trx_started, TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS secs,
       trx_rows_locked, trx_mysql_thread_id, LEFT(trx_query,120) AS q
FROM information_schema.innodb_trx ORDER BY trx_started LIMIT 10;
```
sys.innodb_lock_waits 直接给出阻塞方与被阻塞方线程号。

③ 止血：动作是终止持锁最久的事务，代价是该事务全部回滚，回滚方式是业务侧重放。
```sql
KILL 12345;         -- 等价 KILL CONNECTION，回滚整个事务
KILL QUERY 12345;   -- 仅终止当前语句，事务仍持锁
```
批量终止前先确认 trx_rows_locked 量级，回滚百万行级事务的耗时可达到分钟级。

③ 根因：三个入口是 innodb_trx 的持锁行数、data_lock_waits 的阻塞链、慢日志中 Lock_time 的分布。互证方式是阻塞方 trx_query 为空但持锁，说明事务在应用层提交阶段或连接被池挂起。

③ 治理：版本层 8.0 用 performance_schema.metadata_locks 观测 MDL；参数层 lock_wait_timeout 对 DDL 会话下调到 5 至 10s 使其快速失败；代码层在事务内不做远程调用，事务时长上限 200ms；架构层加长事务巡检脚本按 30s 阈值告警。验收口径是 60s 以上事务日均为 0。
方案取舍：终止事务见效秒级、代价是业务失败；下调超时参数见效分钟级、代价是高峰期误伤。

④ 延伸与边界：失效条件一是连接池在事务提交后未归还连接，此时 innodb_trx 看不到该事务但锁未释放，现象是锁等待持续而查不到长事务。失效条件二是只读事务持有 MDL，DDL 侧表现为等待而非 1205。更深机制点是 purge 线程被长事务的最旧读视图阻塞，undo 无法回收，表现为 ibdata 与 undo 表空间持续增长，这是锁问题的次生现象。相邻场景差异是本单元的处置手段适用于 A3 的死锁残留等待，但不适用于 A2 的双写冲突，后者需要只读约束而非终止事务。

⑤ 常见误述与校准：说法「1205 与 1213 是一回事」不成立，因为前者无环、后者成环；正确表述是两者错误码、回滚范围、处置手段均不同。说法「加索引能消除锁等待」不成立，因为锁范围缩小但持锁时长未变；正确表述是先降持锁时长再谈范围。

⑥ 抓手：先量持锁时长，再谈锁范围。

### A5 连接数打满

① 结论：连接打满多为池上限与慢 SQL 叠加，扩容只买到分钟级时间。

② 为什么：max_connections 限制的是并发连接数，超出时新建连接返回 1040；每个连接占用线程栈与若干会话缓冲区，连接数与内存占用近似线性；Threads_running 反映真正在执行的线程，连接数高而 running 低说明连接在等待而非计算；连接池的 maximumPoolSize 是单实例上限，集群总连接数等于实例数乘池上限；back_log 控制未完成握手的排队队列，队列溢出表现为握手超时而非 1040。

③ 判据：Threads_connected 达到 max_connections 的 80%，或 Aborted_connects 与 Connection_errors_max_connections 持续上升。
```sql
SHOW GLOBAL VARIABLES LIKE 'max_connections';
SHOW GLOBAL STATUS WHERE Variable_name IN
 ('Threads_connected','Threads_running','Max_used_connections',
  'Aborted_connects','Connection_errors_max_connections');
SELECT command, COUNT(*) FROM information_schema.processlist GROUP BY command;
```

③ 止血：动作是清理 Sleep 超过 300s 的连接并临时抬高上限，代价是内存占用上升，回滚方式是恢复原值。
```sql
SET GLOBAL max_connections=1000;   -- 8.0 可 SET PERSIST 持久化
SELECT id FROM information_schema.processlist WHERE command='Sleep' AND time>300;
```
8.0.14 起可启用管理接口（admin_address、admin_port）保留应急通道。

③ 根因：三个入口是 processlist 的状态分布、慢查询日志的时间分布、应用侧池配置。互证方式是连接数高且大量处于 Waiting for table metadata lock 或 Sending data，指向 SQL 层而非连接泄漏。

③ 治理：版本层用 8.0 的管理端口与连接属性；参数层 max_connections 按 实例内存 除以 单连接内存 保守估算；代码层池上限按 数据库上限 除以 应用实例数 再打 7 折；架构层加连接代理与限流。验收口径是 Max_used_connections 长期低于上限的 70%。
方案取舍：抬高上限见效秒级、代价是内存与上下文切换；治理慢 SQL 见效天级、回滚成本低、收益持久。

④ 延伸与边界：失效条件一是连接处于 Sleep 且由池持有，KILL 后被池立即重建，现象是连接数回落即反弹。失效条件二是使用线程池插件时排队发生在池内，数据库侧看不到 1040。更深机制点是每个连接的身份认证在 8.0 默认使用 caching_sha2_password，首次认证需要完整 RSA 交换，连接风暴时握手开销会先于连接数触顶。相邻场景差异是 A6 的 OOM 同样表现为连接异常，但 OOM 会先出现内存指标恶化与进程消失，A5 不会。

⑤ 常见误述与校准：说法「连接数打满就调大 max_connections」不成立，因为根因多为慢 SQL 占坑；正确表述是先降 Threads_running 再调上限。说法「连接数等于并发」不成立，因为多数连接处于 Sleep；正确表述是并发看 Threads_running。

⑥ 抓手：先看 running，再看 connected。

### A6 内存 OOM 与进程被杀

① 结论：OOM 杀手介入前，buffer pool 与连接内存早已把系统余量吃空。

② 为什么：操作系统在可用内存低于水位时按 oom_score 选择进程终止，MySQL 因常驻内存大而优先中选；InnoDB 缓冲池是预分配结构，innodb_buffer_pool_size 调大后即占用虚拟与物理内存，8.0 支持在线扩缩但以 128MB 块为单位；单连接内存由 read_buffer_size、sort_buffer_size、join_buffer_size、binlog_cache_size 等按需分配，峰值出现在排序与连接操作；临时表引擎在 8.0 默认 TempTable，超限后落盘；内存分配失败时错误日志出现 cannot allocate memory，进程可能被内核直接终止而不留 InnoDB 状态。

③ 判据：dmesg 或系统日志存在 Out of memory: Killed process 记录，且错误日志时间点吻合。
```bash
dmesg -T | grep -i -E 'oom|killed process'
```
```sql
SELECT * FROM sys.memory_global_total;
SELECT event_name, current_alloc FROM sys.memory_global_by_current_bytes LIMIT 10;
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_pages_free';
```

③ 止血：动作是限制连接数与并发、临时下调 buffer pool，代价是命中率下降，回滚方式是逐级恢复。
```sql
SET GLOBAL innodb_buffer_pool_size=34359738368;  -- 32G，按块调整
```

③ 根因：三个入口是系统内存曲线、MySQL 内存汇总视图、单连接缓冲参数。互证方式是 buffer pool 占用稳定而进程 RSS 持续上涨，指向连接级分配或内存泄漏类问题。

③ 治理：版本层升级到 8.0 以获得更细的 memory instrument；参数层 buffer pool 设为物理内存的 50% 至 70%，并显式压低 sort_buffer_size 与 join_buffer_size；代码层禁止大结果集排序与超大 IN 列表；架构层为实例设置 cgroup 内存上限并保留系统余量。验收口径是连续 30 天 RSS 峰值低于物理内存的 80%。
方案取舍：降 buffer pool 立即生效、代价是读放大；拆分实例周期长、代价是改造成本。

④ 延伸与边界：失效条件一是容器环境未设置内存限制，现象是节点级 OOM 影响同机其他服务。失效条件二是开启大量并发排序，单连接缓冲叠加可在 buffer pool 稳定时仍触发 OOM。更深机制点是内存分配器的碎片与 jemalloc 与 glibc 的差异会改变 RSS 与虚拟内存的比例，因此看 VSZ 会高估实际占用。相邻场景差异是 A10 的崩溃恢复由掉电或进程崩溃触发，OOM 属于进程被外部终止，恢复路径相同但 redo 应用量取决于刷盘参数。

⑤ 常见误述与校准：说法「buffer pool 越大越好」不成立，因为系统余量不足会触发 OOM；正确表述是留出 20% 以上系统内存。说法「OOM 是 MySQL 内存泄漏」不成立，因为多数是参数叠加；正确表述是先核算单连接峰值内存。

⑥ 抓手：先留系统余量，再谈缓存命中。

### A7 复制中断（1062 / 1032 / 1236）

① 结论：复制中断按错误码分类处置，跳过事务是最后手段且必须留证据。

② 为什么：1062 表示从库已存在相同唯一键，通常源于主库执行过从库未执行的写入或双写；1032 表示按行镜像找不到目标行，说明主从数据已分叉；1236 表示无法读取 binlog，常见于主库已 PURGE 掉从库尚未拉取的位置或 GTID 集合不连续；SQL 线程停止后 relay log 仍会继续接收，因此中断越久恢复时的追赶量越大；跳过计数在 GTID 模式下不适用，需用空事务注入。

③ 判据：Last_SQL_Errno 非 0 且 Replica_SQL_Running 为 No。
```sql
SHOW REPLICA STATUS\G
-- 8.0.22 起字段术语改为 Source，字段名需按版本确认
```
关注 Last_SQL_Errno、Last_SQL_Error、Retrieved_Gtid_Set、Executed_Gtid_Set、Relay_Log_File 与 Relay_Log_Pos。

③ 止血：动作是按错误码定向修复，代价是可能引入新的不一致，回滚方式是重建复制。
```sql
-- 非 GTID 且确认为单条冲突
STOP REPLICA; SET GLOBAL sql_slave_skip_counter=1; START REPLICA;
-- GTID 模式：注入空事务
STOP REPLICA;
SET GTID_NEXT='3E11FA47-71CA-11E1-9E33-C80AA9429562:1001';
BEGIN; COMMIT;
SET GTID_NEXT='AUTOMATIC'; START REPLICA;
```
1236 的处置是重建从库或从备份加 binlog 回放，跳过无效。

③ 根因：三个入口是错误消息中的库表主键、主库同时段 binlog、校验工具的差异报告。互证方式是用 pt-table-checksum 确认差异范围，若差异仅限该行则按单行修复，若成块则重建。

③ 治理：版本层用 8.0 的 GTID 与 replica_skip_errors 白名单；参数层 binlog_expire_logs_seconds 大于最大从库重建窗口；代码层禁止在从库执行写操作，唯一键冲突前置校验；架构层部署延迟从库与校验任务。验收口径是复制中断次数按月下降，校验差异行数为 0。
方案取舍：跳过事务生效秒级、风险是数据继续分叉；重建从库生效小时级、结果确定。

④ 延伸与边界：失效条件一是 relay_log_recovery 开启时重启会丢弃未应用 relay log，现象是重启后 GTID 缺口扩大。失效条件二是级联复制下中间节点跳过会传导到末端。更深机制点是行复制依赖 binlog_row_image，FULL 才携带完整前后镜像，MINIMAL 下 1032 无法定位差异列。相邻场景差异是 A2 的分叉检测同样用 GTID 差集，但处置目标是回补而非跳过。

⑤ 常见误述与校准：说法「跳过错误即可恢复」不成立，因为跳过只让 SQL 线程继续而不修复数据；正确表述是跳过必须记录 GTID 并后续校验。说法「1236 可以跳过」不成立，因为缺失的是整段事件。

⑥ 抓手：先分类错误码，再决定是否跳过。

### A8 误删数据与误更新

① 结论：恢复路径是备份加 binlog 回放，闪回工具只是把回放自动化。

② 为什么：ROW 格式 binlog 记录行镜像，binlog_row_image=FULL 时携带完整前后值，才能由工具生成反向语句；反向语句的执行顺序必须与原事务相反，同一事务内多行更新的中间态无法还原；binlog 中事件时间戳来自主库时钟，跨时区与主从时钟偏差会导致时间窗定位错误；DELETE 与 DROP 的恢复代价不同，DROP 表需先重建表结构再回放；误操作后继续写入会让回放冲突，因此必须先隔离写入。

③ 判据：以误操作时间点为锚，binlog 中定位到对应事件。
```bash
mysqlbinlog --base64-output=DECODE-ROWS -vv \
  --start-datetime='2026-11-02 10:00:00' --stop-datetime='2026-11-02 10:05:00' \
  mysql-bin.000123 | less
```
判定异常的依据是事件中出现目标表名与大批量行镜像。

③ 止血：动作是立即停止该表写入并对表加写锁，代价是业务中断，回滚方式是恢复后解锁。
```sql
LOCK TABLES t WRITE;      -- 会话级，需保持会话
FLUSH TABLES t WITH READ LOCK;
```
```bash
binlog2sql -h host -u user -p pass --start-file=mysql-bin.000123 \
  --start-datetime='2026-11-02 10:00:00' --stop-datetime='2026-11-02 10:05:00' -B -d db -t t
```

③ 根因：三个入口是 binlog 事件、备份时间点、应用操作日志。互证方式是 binlog 中的线程号与业务账号可对应到具体请求。

③ 治理：版本层用 8.0 的 binlog 事务压缩与更完整的 GTID 标记；参数层 binlog_format=ROW、binlog_row_image=FULL、保留期覆盖最大回滚窗口；代码层禁止直连生产执行 DML，删除走软删除；架构层部署延迟 1 小时的延迟从库作为回滚缓冲。验收口径是恢复演练达到 30 分钟内完成单表回灌。
方案取舍：延迟从库见效即时、代价是资源；binlog 回放精确但耗时长。

④ 延伸与边界：失效条件一是 binlog_format=STATEMENT 时无法生成反向语句，现象是只能按时间点整体回放。失效条件二是 DDL 混入时间窗，回放会重建对象并丢失后续写入。更深机制点是 binlog 的组提交顺序决定同一秒内事务的先后，回放必须按 XID 逆序才能保持一致性。相邻场景差异是本单元与 A12 的 PITR 共用工具链，但 A12 面向全实例恢复，本单元面向单表定向修复。

⑤ 常见误述与校准：说法「闪回工具能撤销一切」不成立，因为无完整行镜像时无法构造反向语句；正确表述是取决于行镜像与格式。说法「DROP 表也能闪回」不成立，因为数据页与索引同时消失；正确表述是 DROP 必须靠备份。

⑥ 抓手：先锁写入，再谈回放。

### A9 磁盘写满

① 结论：写满九成来自 binlog、临时表与大 undo，处置顺序是先降增速再删文件。

② 为什么：binlog 按 max_binlog_size 滚动，单个文件上限不限制总量，总量由保留期决定；大事务在 binlog_cache_size 溢出后写临时文件，与 binlog 共同占用数据目录；内部临时表超过 temptable_max_ram 后使用 mmap 或落盘，超限时错误 1114 出现；undo 表空间随长事务增长，innodb_undo_log_truncate 只在事务结束后才可截断；ibdata 一旦扩展不会自动收缩。

③ 判据：数据目录所在分区使用率超过 90%，且 1 小时内增速超过 1G。
```bash
df -h /var/lib/mysql
du -sh /var/lib/mysql/* | sort -h | tail
```
```sql
SHOW BINARY LOGS;
SELECT SUM(file_size)/1024/1024 AS mb FROM performance_schema.temp_tables;
```
8.0 中 performance_schema.temp_tables 的部分列需按版本确认。

③ 止血：动作是清理过期 binlog 与临时文件，代价是破坏复制与回滚能力，回滚方式无法回滚，须先确认从库已消费。
```sql
PURGE BINARY LOGS BEFORE NOW() - INTERVAL 1 DAY;
SET GLOBAL binlog_expire_logs_seconds=86400;  -- 8.0；5.7 为 expire_logs_days
```
文件系统层面删除文件前必须确认对应对象已关闭，否则空间不释放。

③ 根因：三个入口是目录占用分布、binlog 生成速率、长事务列表。互证方式是 binlog 增速与写入 QPS 同步，指向业务量；与 QPS 无关则指向大事务或全镜像更新。

③ 治理：版本层 8.0 使用 binlog 事务压缩减少体积；参数层按从库最大重建时间设定保留期；代码层禁止无 WHERE 的批量更新与长期未提交事务；架构层数据盘与日志盘分离并设置水位告警。验收口径是数据盘长期低于 75%。
方案取舍：缩短保留期见效秒级、风险是复制断裂；扩容磁盘见效分钟级、成本上升。

④ 延伸与边界：失效条件一是文件已被删除但句柄未释放，df 与 du 结果不一致。失效条件二是表空间自动扩展写满挂载点，现象是插入报错而非查询失败。更深机制点是 InnoDB 的预分配与双写缓冲（doublewrite）会额外占用与脏页同量级的空间，容量估算需计入该部分。相邻场景差异是 A10 的崩溃恢复同样依赖 redo 空间，磁盘满会导致 redo 无法写入并触发只读保护。

⑤ 常见误述与校准：说法「删日志文件即可释放」不成立，因为句柄未关闭；正确表述是先 PURGE 再观察 df。说法「磁盘满只影响写入」不成立，因为临时表与排序同样失败。

⑥ 抓手：先看增速，再看占用。

### A10 宕机与崩溃恢复

① 结论：崩溃恢复是 redo 前滚加 undo 回滚，双一参数决定已提交事务丢不丢。

② 为什么：redo 记录页级物理变更，崩溃后按 checkpoint 位置前滚到一致状态，再按 undo 回滚未提交事务；innodb_flush_log_at_trx_commit=1 时每次提交刷盘，等于 0 或 2 会以秒级窗口丢事务；sync_binlog=1 保证 binlog 与 redo 的提交顺序一致，否则可能出现从库已收到而主库未落盘；8.0.30 起 redo 由 innodb_redo_log_capacity 统一管理，容量决定恢复时需前滚的量；双写缓冲保证页断裂可恢复，关闭后掉电可能产生页损坏。

③ 判据：错误日志中出现 Starting crash recovery 与 redo 应用进度，且 SHOW ENGINE INNODB STATUS 的 Last checkpoint at 与日志序列号推进。
```sql
SHOW ENGINE INNODB STATUS\G   -- 看 LOG 段的 Log sequence number 与 Last checkpoint at
SHOW GLOBAL VARIABLES WHERE Variable_name IN
 ('innodb_flush_log_at_trx_commit','sync_binlog','innodb_redo_log_capacity');
```

③ 止血：动作是启动后限制接入流量，等待 redo 应用结束，代价是恢复时间不可压缩。
```sql
SET GLOBAL max_connections=50;
SET GLOBAL innodb_force_recovery=1;  -- 仅在无法启动时逐级尝试，1 至 6
```
innodb_force_recovery 大于 0 时实例只读，回滚方式是导出数据后重建实例。

③ 根因：三个入口是错误日志的恢复明细、redo 容量与 checkpoint 间隔、掉电前的写入压力。互证方式是恢复耗时与 redo 容量成正比，可判定为刷盘策略问题而非磁盘故障。

③ 治理：版本层 8.0.30 以上使用统一 redo 容量参数；参数层保持双一为 1，redo 容量按峰值写入量乘 1 小时的量级设定；代码层控制单事务大小以缩短前滚时间；架构层做掉电演练与主从切换演练。验收口径是模拟 kill -9 后恢复时间低于 60s 且数据零丢失。
方案取舍：调大 redo 提升写入吞吐、代价是恢复变慢；保持双一安全、代价是提交延迟。

④ 延伸与边界：失效条件一是 innodb_flush_method 与文件系统缓存叠加，落盘语义被文件系统缓存改写。失效条件二是 redo 容量过大而磁盘 IO 不足，恢复时间可达小时级。更深机制点是组提交把多个事务的 redo 合并为一次 fsync，因此并发越高单位提交成本越低，低并发下双一的延迟更明显。相邻场景差异是 A6 的进程被杀不涉及页损坏，A10 的掉电场景必须考虑页断裂。

⑤ 常见误述与校准：说法「双一关掉更快且无损」不成立，因为崩溃会丢已提交事务；正确表述是性能与 RPO 的显式取舍。说法「崩溃恢复一定成功」不成立，因为页损坏需双写缓冲支撑。

⑥ 抓手：先看双一，再谈恢复时长。

### A11 从库只读失效与读写分离踩坑

① 结论：只读失效根因是 read_only 挡不住超级用户，路由错乱根因是中间件缓存。

② 为什么：read_only 对具备 SUPER 权限的账号无效，super_read_only 才覆盖；复制线程本身不受只读限制，因此从库仍可接收主库变更；中间件在连接建立时确定后端，事务内跨语句可能落到不同节点；读写分离的一致性依赖 GTID 等待，未等待时会读到旧值；某些中间件把 DDL 与 SELECT 分派到不同节点，导致元数据不一致。

③ 判据：从库 read_only 或 super_read_only 为 OFF，且从库 gtid_executed 出现非主库来源的事务。
```sql
SELECT @@global.read_only, @@global.super_read_only;
SELECT @@global.gtid_executed;
```
中间件侧查看路由日志中同一事务是否命中多个后端。

③ 止血：动作是置只读并清理业务直连，代价是部分读请求失败，回滚方式是恢复配置。
```sql
SET GLOBAL super_read_only=ON;
SET PERSIST read_only=ON;   -- 8.0 持久化，重启仍生效
```

③ 根因：三个入口是只读变量、连接来源地址、中间件规则。互证方式是直连从库写入成功即证明权限绕过。

③ 治理：版本层 8.0 的 SET PERSIST 保证重启后仍只读；参数层默认开启 super_read_only 并由编排器在切换时解除；代码层禁止应用配置从库地址；架构层读写分离统一走代理并启用 GTID 等待。验收口径是从库写入尝试 100% 失败。
方案取舍：代理层强制只读生效即时、代价是引入单点；应用层约束成本低但不可靠。

④ 延伸与边界：失效条件一是主从切换脚本遗漏只读开关，现象是切换后旧主可写。失效条件二是 GTID 等待超时被忽略，现象是只读正确但读到旧数据。更深机制点是代理的连接复用会在事务边界外复用后端连接，事务内的读一致性依赖代理对事务状态的识别能力。相邻场景差异是 A2 的双写同样表现为从库可写，但 A2 伴随两侧 GTID 分叉。

⑤ 常见误述与校准：说法「设了 read_only 就安全」不成立，因为超级用户绕过；正确表述是用 super_read_only 加账号收敛。

⑥ 抓手：只读要防超级用户。

### A12 备份恢复与 RPO / RTO

① 结论：RPO 由 binlog 落盘与备份周期决定，RTO 由恢复链路串行步骤决定。

② 为什么：物理备份的一致性依赖备份期间的 redo 与 undo 一致性点，xtrabackup 通过记录 LSN 并在 prepare 阶段前滚实现；逻辑备份的一致性依赖 single-transaction 的一致性快照，DDL 会破坏该快照；RPO 的构成是备份周期与 binlog 落盘策略，sync_binlog=1 时已提交事务的 RPO 接近 0；RTO 的构成是备份传输、prepare、copy-back、redo 回放、binlog 回放五段串行耗时；克隆插件在 8.0.17 起可在实例间直接物理复制。

③ 判据：以最近一次演练的实际恢复时间为准，不以备份成功日志为准。
```bash
xtrabackup --backup --target-dir=/backup/full --user=root --password=***
xtrabackup --prepare --target-dir=/backup/full
xtrabackup --copy-back --target-dir=/backup/full
```
```sql
CLONE INSTANCE FROM 'user'@'host':3306 IDENTIFIED BY 'pwd';
```
判定异常的依据是 prepare 阶段报 LSN 不连续，或回放 binlog 时出现重复键。

③ 止血：动作是从最近可用备份加 binlog 回放到故障点，代价是数据缺口为备份周期内未落盘部分。
```bash
mysqlbinlog --start-position=... --stop-position=... mysql-bin.000124 | mysql -uroot -p
```

③ 根因：三个入口是备份校验结果、binlog 完整性与恢复耗时分解。互证方式是按段计时，找出占比最高的环节。

③ 治理：版本层用 8.0 克隆插件缩短 RTO；参数层按 RTO 目标反推备份频率与 binlog 保留期；代码层把 DDL 变更排除在备份窗口外；架构层每季度全量演练并记录 RTO。验收口径是单实例 500GB 数据恢复时间低于 30 分钟，RPO 低于 1 分钟。
方案取舍：物理备份恢复快、体积大；逻辑备份可选择性恢复、耗时长。

④ 延伸与边界：失效条件一是备份与 binlog 分属不同实例时钟，回放定位偏差。失效条件二是表使用非事务引擎，一致性快照无效。更深机制点是 prepare 阶段的前滚只处理已提交事务的 redo，未提交事务在恢复时由 undo 回滚，因此备份期间的长事务会显著拉长 prepare。相邻场景差异是 A8 的单表回灌可只回放部分事件，A12 面向全实例，回放范围不可裁剪。

⑤ 常见误述与校准：说法「备份成功即可用」不成立，因为未验证的备份不可恢复；正确表述是以演练恢复为准。说法「RPO 由备份频率单因素决定」不成立，因为还取决于 binlog 落盘。

⑥ 抓手：备份不以成功为准，以恢复为准。

## 4. B 部分逐单元详解

### B1 慢查询日志开启与采集

链路节点：1，慢日志采集。

① 结论：慢日志是唯一可回溯的全量证据源，阈值按耗时分布定而非按默认值。

② 为什么：long_query_time 判定的是语句执行耗时而非锁等待耗时，Lock_time 单独记录；log_queries_not_using_indexes 会把扫描行数少但未走索引的语句也写入，日志量会放大数倍；min_examined_row_limit 可反向过滤低扫描语句；8.0 的 log_slow_extra 在日志中追加更多字段，便于区分解析与执行阶段；日志写入文件与写入 mysql.slow_log 表互斥由 log_output 控制，写表会带来额外开销。

③ 判据：慢日志覆盖至少 24 小时且单日条目数在万级以内，能支撑排序分析。
```sql
SET GLOBAL slow_query_log=ON;
SET GLOBAL long_query_time=0.1;
SET GLOBAL log_output='FILE';
SET GLOBAL log_slow_extra=ON;           -- 8.0
SET GLOBAL min_examined_row_limit=100;
SHOW VARIABLES LIKE '%slow%';
```
判定异常的依据是日志中出现 Query_time 大于 1 且 Rows_examined 远大于 Rows_sent。

③ 止血：动作是临时把阈值降到 0.1 采集一轮，代价是写放大，回滚方式是恢复原阈值。

③ 根因：三个入口是日志文件、digest 视图与业务时间线。互证方式是日志中耗时峰值与业务发布记录对齐。

③ 治理：参数层阈值按 P99 的 1 至 2 倍设定并定期复核；代码层压测环境同样开启；架构层日志集中采集并保留 7 天。验收口径是每周可产出 Top20 耗时 SQL。
方案取舍：写文件开销低、回滚容易；写表查询方便但影响性能。

④ 延伸与边界：失效条件一是阈值设为 10s（默认）导致长尾全部漏采。失效条件二是复制线程执行的语句默认不记录，8.0 需要 log_replica_statements。更深机制点是耗时统计在语句结束处一次性写入，被 KILL 的语句可能不落日志。相邻场景差异是 B7 的锁等待时间不计入 Query_time，因此慢日志看不出被锁拖慢的语句。

⑤ 常见误述与校准：说法「慢日志等于慢查询全集」不成立，因为锁等待与网络耗时不入 Query_time；正确表述是慢日志反映执行耗时。

⑥ 抓手：阈值不降，证据不全。

### B2 慢日志聚合分析

链路节点：2，聚合排序。

① 结论：按总耗时排序而非平均耗时排序才能找到真瓶颈。

② 为什么：digest 视图把字面量归一化为占位符，同一模板的多次执行被聚合；SUM_TIMER_WAIT 以皮秒为单位，需除以 1e12 得到秒；平均耗时高但频次极低的语句对总负载贡献有限；COUNT_STAR 与 SUM_ROWS_EXAMINED 的比值反映单次扫描量；pt-query-digest 按 Query_time 总和排序并给出方差，方差大说明执行计划不稳定。

③ 判据：Top1 digest 的总耗时占全库总耗时 5% 以上，或单条平均耗时超过 100ms 且频次进入前 10。
```sql
SELECT DIGEST_TEXT, COUNT_STAR,
       SUM_TIMER_WAIT/1e12 AS total_s,
       SUM_ROWS_EXAMINED, SUM_NO_INDEX_USED
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 20;
```
```bash
pt-query-digest --since=24h --order-by=Total --limit=20 slow.log
```

③ 止血：动作是对 Top 语句先加限流或缓存，代价是数据新鲜度下降。

③ 根因：三个入口是 digest 总耗时、扫描行数、执行频次。互证方式是总耗时高且扫描行数高指向索引问题，总耗时高但扫描行数低指向锁或返回量大。

③ 治理：参数层开启 performance_schema 的语句统计并定期采样；代码层建立 SQL 准入评审；架构层把 digest 报表接入发布流程。验收口径是 Top10 总耗时占比逐月下降。
方案取舍：digest 视图实时但重启清零；pt-query-digest 可回溯历史但依赖日志保留。

④ 延伸与边界：失效条件一是 performance_schema 的 digest 表容量有限，长尾被淘汰。失效条件二是语句文本差异过大导致归一化失效，现象是同一业务出现多个 digest。更深机制点是 digest 计算在语句结束时的 hash 阶段完成，绑定变量的语句归一化更彻底。

⑤ 常见误述与校准：说法「平均耗时最高的最该优化」不成立，因为频次决定总量贡献。

⑥ 抓手：先看总量，再看单条。

### B3 EXPLAIN 各列含义

链路节点：3，EXPLAIN 静态计划。

① 结论：type 与 rows 是静态计划的第一判据，Extra 决定是否需要回表。

② 为什么：type 按访问方式从 system、const、eq_ref、ref、range、index 到 ALL 依次变差，index 表示全索引扫描仍要读全部索引项；key_len 反映使用的索引前缀长度，可用于判断联合索引用到第几列；rows 是优化器估算的扫描行数，不是返回行数；filtered 表示经过条件过滤后的比例，rows 乘 filtered 才是估算返回量；Extra 中 Using index 表示覆盖索引无需回表（回表，Bookmark Lookup），Using filesort 与 Using temporary 表示额外排序与临时表。

③ 判据：type 为 ALL 或 index 且 rows 超过 10 万，判定为需要处理。
```sql
EXPLAIN FORMAT=TREE SELECT ...;
EXPLAIN FORMAT=JSON SELECT ...;
SHOW WARNINGS;
```
格式为 TREE 时关注 cost 与 rows 的组合。

③ 止血：动作是对该类语句加超时与限流，代价是功能降级。

③ 根因：三个入口是 EXPLAIN 输出、表结构与索引定义、SHOW WARNINGS 中的改写结果。互证方式是 SHOW WARNINGS 显示条件被改写后索引列参与运算，则 B5 类问题成立。

③ 治理：参数层固定 optimizer_switch 关键项避免计划漂移；代码层 SQL 评审包含 EXPLAIN 步骤；架构层建立索引与语句的对应台账。验收口径是核心接口语句 type 不劣于 range。
方案取舍：加索引见效分钟级、代价是写放大；改 SQL 见效天级、收益更稳。

④ 延伸与边界：失效条件一是数据分布倾斜，rows 估算与实际差异极大。失效条件二是 EXPLAIN 不执行语句，因此无法反映锁等待与临时表溢出。更深机制点是优化器以页为单位估算 IO 成本，故 rows 与实际读页数并非线性对应。相邻场景差异是 B4 的实际执行统计才能反映真实行数，B3 只给静态判断。

⑤ 常见误述与校准：说法「key 有值即走对索引」不成立，因为可能只用到前缀列；正确表述是结合 key_len 与 rows 判断有效前缀。

⑥ 抓手：type 定方式，rows 定量级。

### B4 EXPLAIN ANALYZE 与估算偏差

链路节点：4，执行计划偏差。

① 结论：估算与真实行数偏差超过 10 倍即视为统计信息失真，需要重估或加直方图。

② 为什么：EXPLAIN ANALYZE 在 8.0.18 起真实执行语句并输出每步的 actual time 与 rows，loops 表示该步被重复次数；优化器基于索引基数与采样页估算选择性，innodb_stats_persistent_sample_pages 默认 20 页，采样不足时基数偏差放大；直方图只对无索引或倾斜列有效，8.0 通过 ANALYZE TABLE 更新；eq_range_index_dive_limit 控制等值范围是否做索引潜水，超限后退化为统计估算，偏差随之出现。

③ 判据：EXPLAIN ANALYZE 输出中某步 rows 估算值与 actual rows 相差 10 倍以上。
```sql
EXPLAIN ANALYZE SELECT ...;
ANALYZE TABLE t UPDATE HISTOGRAM ON c WITH 128 BUCKETS;
SET optimizer_trace='enabled=on';
SELECT * FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace='enabled=off';
```

③ 止血：动作是对该语句临时固定索引，代价是失去灵活性，回滚方式是删除 hint。

③ 根因：三个入口是 ANALYZE 输出、直方图与索引基数、trace 中的代价计算。互证方式是基数与实际 distinct 值差异大，则确认为统计失真。

③ 治理：参数层提高采样页数并开启自动重算；代码层对倾斜列建直方图；架构层定期执行统计信息巡检。验收口径是 Top 语句的行数偏差低于 3 倍。
方案取舍：加直方图见效分钟级、代价是统计维护成本；改写 SQL 见效天级、收益稳定。

④ 延伸与边界：失效条件一是表数据量小，采样页已覆盖全表，偏差不出现。失效条件二是查询含子查询与非确定函数，ANALYZE 的重复执行结果不可比。更深机制点是优化器的成本模型以随机读与顺序读的代价常数为基础，SSD 上该常数偏移会导致系统性误判。相邻场景差异是 B6 的选错索引正是偏差的下游后果。

⑤ 常见误述与校准：说法「ANALYZE TABLE 能解决所有偏差」不成立，因为基数准确不等于代价模型准确。

⑥ 抓手：估算偏差过十倍，先重估再改 SQL。

### B5 索引失效的全部典型场景

链路节点：5，索引与改写修正。

① 结论：索引失效几乎都发生在索引列被运算、被转换或前缀失配上。

② 为什么：索引按列值有序存储，列上套函数后该顺序与函数结果无关，优化器无法用 B+ 树定位；隐式类型转换把字符串列与数字比较时按浮点比较，等价于列上套函数；联合索引遵循最左前缀，跳过首列后无法定位；LIKE 以通配符开头时无法做范围定位；OR 连接非索引列时退化为全表扫描；排序方向与索引顺序不一致时产生额外排序。

③ 判据：EXPLAIN 的 key 为 NULL 或 type 为 ALL，且 WHERE 中存在索引列。
```sql
EXPLAIN SELECT ...;
SHOW WARNINGS;                      -- 查看隐式转换提示
SELECT * FROM t WHERE date_col >= '2026-01-01';   -- 正确写法
SELECT * FROM t WHERE DATE(date_col) = '2026-01-01';  -- 失效写法
```
8.0 可用函数索引：
```sql
ALTER TABLE t ADD INDEX idx_lower_name ((LOWER(name)));
```

③ 止血：动作是把语句改写为范围条件或加函数索引，代价是 DDL 期间占用资源。

③ 根因：三个入口是 EXPLAIN、SHOW WARNINGS、表结构与列类型。互证方式是对比改写前后 rows 变化，若 rows 从百万降到千级则确认失效原因。

③ 治理：代码层统一日期与字符串的参数类型，禁止列上运算；参数层关注字符集与排序规则一致性；架构层建立索引失效的静态扫描规则。验收口径是核心 SQL 的 key 均非 NULL。
方案取舍：改写 SQL 见效即时、无副作用；函数索引见效分钟级、代价是写放大与版本限制。

④ 延伸与边界：失效条件一是 8.0 的函数索引让部分运算重新可用，此现象在 5.7 不成立。失效条件二是数据量极小，全表扫描代价低于索引扫描，优化器主动放弃索引。更深机制点是索引选择性低于阈值时，优化器按页代价选择全表，因此低基数列建索引无效。相邻场景差异是 B6 的选错索引是索引存在但未被选，与本单元的索引不可用不同。

⑤ 常见误述与校准：说法「建了索引就一定走」不成立，因为可用性与被选是两件事。

⑥ 抓手：列上不运算，类型不混用。

### B6 执行计划选错索引

链路节点：5，索引与改写修正。

① 结论：选错索引多因统计信息失真与回表代价误估，force index 只作临时手段。

② 为什么：优化器按索引基数估算过滤后的行数，再叠加回表随机读代价，选择总代价最低的方案；当索引覆盖查询时不需要回表，代价显著低于选择性更高的索引；索引潜水在等值条件数超过 eq_range_index_dive_limit 时退化为统计估算；统计信息在 innodb_stats_auto_recalc 开启时异步重算，存在滞后窗口；force index 固化选择后，数据分布变化会导致新的劣化。

③ 判据：存在选择性更优的索引但 EXPLAIN 选择另一个，且实际耗时超过预期 3 倍。
```sql
SHOW INDEX FROM t;
SELECT * FROM mysql.innodb_index_stats WHERE table_name='t';
SELECT * FROM sys.schema_unused_indexes;
SELECT * FROM sys.schema_redundant_indexes;
```

③ 止血：动作是临时 ANALYZE TABLE 或加 force index，代价是计划僵化，回滚方式是删除 hint。

③ 根因：三个入口是基数与实际 distinct、代价 trace、回表行数。互证方式是实际回表行数远大于估算，则确认为代价误估。

③ 治理：参数层调整采样页与统计自动重算；代码层对倾斜列建直方图并避免冗余索引；架构层定期清理未使用索引。验收口径是核心语句计划稳定，无周级漂移。
方案取舍：force index 见效秒级、风险是僵化；重估统计见效分钟级、可持续。

④ 延伸与边界：失效条件一是表数据量激增后原索引选择性下降，原计划不再最优。失效条件二是覆盖索引出现，原回表代价估算不再适用。更深机制点是优化器对随机读的代价常数在 SSD 上偏保守，导致倾向全表扫描。相邻场景差异是本单元与 B5 的边界在于索引是否可用。

⑤ 常见误述与校准：说法「force index 是最佳实践」不成立，因为数据变化后必须人工复查。

⑥ 抓手：选错先重估，再考虑固化。

### B7 锁与事务把快查询拖成慢查询

链路节点：1 与 3 之间的横向分支，以 Lock_time 占比识别。

① 结论：快查询变慢多数不是执行慢，而是等待锁与元数据锁。

② 为什么：Lock_time 统计的是语句在 server 层等待表锁与元数据锁的时间，行锁等待计入 InnoDB 内部而不完全体现在该字段；MDL 在语句解析阶段申请，被长事务或未提交的 DDL 阻塞时状态显示 Waiting for table metadata lock；可重复读下的范围更新会加间隙锁，阻塞插入；长事务持有的最旧读视图会阻止 purge，历史版本链变长后一致性读需回溯更多版本。

③ 判据：慢日志中 Lock_time 占 Query_time 的 30% 以上，或 processlist 中大量会话处于元数据锁等待。
```sql
SELECT * FROM sys.schema_table_lock_waits\G
SELECT * FROM performance_schema.metadata_locks WHERE LOCK_STATUS='PENDING';
SELECT * FROM sys.innodb_lock_waits\G
```

③ 止血：动作是终止阻塞源会话，代价是该会话事务回滚。

③ 根因：三个入口是锁等待视图、长事务列表、DDL 执行记录。互证方式是阻塞方为一条未提交的 SELECT 或一个 DDL，则确认。

③ 治理：参数层下调 lock_wait_timeout 使 DDL 快速失败；代码层禁止在事务中执行 DDL 与长查询；架构层把 DDL 纳入变更窗口。验收口径是元数据锁等待时长低于 5s。
方案取舍：终止会话见效秒级、代价是业务失败；改事务边界见效天级、收益彻底。

④ 延伸与边界：失效条件一是只读查询在 RC 下几乎不持锁，此类等待不会出现。失效条件二是连接池挂起导致事务未提交，锁等待视图可见而长事务视图不可见。更深机制点是 MDL 的申请顺序决定死锁，两个会话分别持有共享与排他元数据锁会互相阻塞。相邻场景差异是 A4 的 1205 属于行锁超时，本单元的等待多为 MDL，无超时上限。

⑤ 常见误述与校准：说法「慢查询都是 SQL 写得差」不成立，因为锁等待与写法无关。

⑥ 抓手：先看 Lock_time，再改 SQL。

### B8 深分页

链路节点：5，分页改写。

① 结论：深分页的代价在于丢弃前 N 行，改写为游标或延迟关联可消除该代价。

② 为什么：LIMIT offset, n 需要读取并丢弃前 offset 行，offset 越大扫描量线性增长；延迟关联先用覆盖索引取出主键再回表，只对最终 n 行回表；游标分页用 WHERE id > last_id 把偏移转为范围条件，扫描量恒定为 n 的量级；ORDER BY 与索引顺序不一致时还会引入额外排序；COUNT 查询在深分页场景常被单独优化为索引扫描。

③ 判据：LIMIT 偏移量超过 1 万且 EXPLAIN 的 rows 接近偏移量。
```sql
-- 延迟关联
SELECT t.* FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 100000,20) x USING(id);
-- 游标分页
SELECT * FROM t WHERE id > 100000 ORDER BY id LIMIT 20;
```

③ 止血：动作是把接口偏移上限收紧并引导游标分页，代价是前端交互变化。

③ 根因：三个入口是 EXPLAIN 的 rows、慢日志的 Rows_examined 与 Rows_sent 比值、接口的翻页参数。互证方式是 Rows_examined 约为偏移量加 n，则确认。

③ 治理：代码层统一改为游标分页并提供上一页能力；参数层对偏移设上限；架构层对导出类需求走异步任务。验收口径是分页接口 P99 与偏移量无关。
方案取舍：游标分页见效天级、代价是改造成本；延迟关联见效小时级、代价是仍需扫描索引。

④ 延伸与边界：失效条件一是排序字段非唯一，游标分页会漏行或重行。失效条件二是业务需要随机跳页，游标方案不适用。更深机制点是覆盖索引扫描虽不回表，但仍需遍历索引页，偏移极大时 IO 仍线性增长。相邻场景差异是 B9 的 DDL 同样会在大表上产生长耗时，但耗时分布集中在单次执行而非线性增长。

⑤ 常见误述与校准：说法「加索引能解决深分页」不成立，因为问题在丢弃行数。

⑥ 抓手：偏移即代价，游标即恒定。

### B9 大表 DDL

链路节点：5，结构变更。

① 结论：DDL 的风险在元数据锁等待与复制延迟，而不在执行时长。

② 为什么：在线 DDL 分 INSTANT、INPLACE、COPY 三类，只有 INSTANT 与部分 INPLACE 不重建表；INPLACE 期间仍短暂申请排他元数据锁以提交变更，等待队列会阻塞后续所有查询；COPY 方式重建表并回放增量，期间写放大与磁盘占用翻倍；主库 DDL 在从库串行执行，单线程回放会使延迟快速抬升；gh-ost 与 pt-online-schema-change 通过影子表与触发器或 binlog 抓取降低锁时间，但引入额外写入与延迟。

③ 判据：DDL 会话状态为 Waiting for table metadata lock，或执行后从库延迟持续上升。
```sql
ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INSTANT;      -- 8.0.12 起支持
ALTER TABLE t ADD INDEX idx_c (c), ALGORITHM=INPLACE, LOCK=NONE;
SELECT * FROM performance_schema.metadata_locks WHERE OBJECT_NAME='t';
```

③ 止血：动作是终止 DDL 会话并选择低峰重试，代价是变更推迟。
```sql
KILL 23456;   -- DDL 会话，回滚可能耗时
```

③ 根因：三个入口是元数据锁视图、从库延迟曲线、DDL 执行计划（ALGORITHM 选择结果）。互证方式是 DDL 执行期间从库 SBM 同步抬升且 worker 单线程繁忙，则确认为复制回放瓶颈。

③ 治理：参数层设置 lock_wait_timeout 让 DDL 快速失败；代码层把 DDL 纳入发布流水线并检查 ALGORITHM；架构层优先使用 gh-ost 并限速。验收口径是 DDL 期间业务 P99 波动低于 10%。
方案取舍：原生在线 DDL 无外部依赖、风险是元数据锁；gh-ost 可控可暂停、代价是额外资源与运维复杂度。

④ 延伸与边界：失效条件一是修改列类型或字符集，无法使用 INSTANT，必须重建。失效条件二是从库并行复制无法覆盖 DDL，延迟必然出现。更深机制点是元数据锁的申请队列按先后排序，一个等待中的 DDL 会阻塞后续所有语句，因此锁等待具有队头阻塞特征。相邻场景差异是 B7 的锁等待来自事务，本单元的等待来自结构变更。

⑤ 常见误述与校准：说法「online DDL 不锁表」不成立，因为提交阶段需要短暂排他锁。

⑥ 抓手：DDL 之险在锁与延迟。

### B10 应用侧放大

链路节点：1 与 2 之间的横向分支，以频次与连接数识别。

① 结论：应用放大来自连接池、N+1、批量提交与缓存击穿四类，均为连接级现象。

② 为什么：连接池上限之和超过数据库上限时，高峰期连接争抢导致排队，表现为 Threads_running 抬升而单条 SQL 并不慢；N+1 使同一模板的调用次数按结果集大小倍增，digest 层面表现为 COUNT_STAR 异常高；批量提交过大导致单事务持有大量行锁并拉长提交时间；缓存击穿使同一热点键的请求同时穿透到数据库，表现为瞬时 QPS 尖峰与相同 digest 并发堆积。

③ 判据：QPS 与 Threads_running 同步抬升，而单条 SQL 的 EXPLAIN 与耗时正常。
```sql
SELECT DIGEST_TEXT, COUNT_STAR FROM performance_schema.events_statements_summary_by_digest
ORDER BY COUNT_STAR DESC LIMIT 10;
SHOW GLOBAL STATUS WHERE Variable_name IN ('Questions','Com_select','Threads_running');
```

③ 止血：动作是对热点接口加单飞与限流，代价是部分请求降级。

③ 根因：三个入口是 digest 频次、连接池监控、缓存命中率。互证方式是同一 digest 的 COUNT_STAR 与页面请求量成正比，则确认为 N+1。

③ 治理：代码层批量查询替代循环单查、批量大小控制在 500 以内、缓存加互斥重建；参数层池上限按数据库上限反推；架构层热点键预热与多级缓存。验收口径是峰值 Questions 与页面 PV 的比值稳定。
方案取舍：缓存互斥见效小时级、代价是首次延迟；批量化见效天级、代价是改造面。

④ 延伸与边界：失效条件一是池上限充足但网络往返多，现象是 QPS 高而数据库 CPU 低。失效条件二是缓存集中过期导致同时击穿，限流只能削峰。更深机制点是连接建立涉及认证与线程创建，短连接模式下握手开销可超过查询本身。相邻场景差异是 A5 的连接打满在数据库侧可见 1040，本单元在池耗尽时表现为应用侧超时。

⑤ 常见误述与校准：说法「数据库慢就是 SQL 慢」不成立，因为放大来自调用次数。

⑥ 抓手：先看次数，再看单条。
