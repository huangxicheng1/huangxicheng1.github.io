## 0. 先明确一个前提：Redis 是内存数据库，一旦重启，内存里的数据就全没了

持久化要解决的问题，是**重启后能否恢复，以及最多能容忍丢多少数据**。

下面拆开讲，最后重点讲 `fork + COW`，这部分是 Redis 持久化里最容易讲不清、也最容易被追问的地方。

---

## 1. RDB：某一时刻的全量快照

### 它是什么

把**某一瞬间**内存里的所有数据，序列化成一个紧凑的二进制文件 `dump.rdb`。

```
时间点 T0：内存有 100 万条数据
     ↓ bgsave
生成 dump.rdb（包含 T0 时刻的全部数据）
```

**注意：RDB 只覆盖生成快照那一刻的内容**。生成快照之后再写入的数据，不在文件里。

### 什么时候触发

| 触发方式 | 说明 |
|---|---|
| `save 900 1` | 配置项：**900 秒内至少有 1 个 key 变更**，就触发 bgsave。默认 `900 1` / `300 10` / `60 10000` |
| `SAVE` 命令 | **同步**执行，主线程阻塞直到写完，**生产环境禁用** |
| `BGSAVE` 命令 | **fork 子进程**后台写，主线程继续服务 |
| `SHUTDOWN` | 正常关机会先做一次快照 |
| **主从全量同步** | 主节点 bgsave 出 RDB 发给从节点 |

三种自动触发条件的含义要能说清：`save 300 10` = "300 秒内只要发生 10 次写，就落一次盘"。所以写入越频繁，快照越频繁。

### 优点

| 优点 | 原因 |
|---|---|
| **文件小** | 二进制 + 紧凑编码，比 AOF 小一个数量级 |
| **恢复快** | 直接反序列化加载进内存，100 万 key 几秒级；AOF 是逐条重放命令 |
| **适合备份/灾备** | 一个文件，直接拷走；也适合跨机房传输（主从同步就用它） |

### 缺点

**核心缺点：两次快照之间写入的数据全部丢失。**

```
T0 快照 → 写入了 5 万条数据 → T0+300s 时宕机
                                   ↑
                          这 5 万条全没了
```

快照间隔是分钟级，所以 RDB 单独用的时候，**可能丢几分钟的数据**。对缓存场景无所谓（丢了回源就行），对存储场景不可接受。

## 2. AOF：把每条写命令追加记录

### 它是什么

不存数据本身，而是**存"怎么变成现在这样"**——每条写命令按顺序追加到文件末尾。

```
文件内容（简化）：
*2 $3 SET $5 user1 $7 {"name":"张三"}
*2 $3 SET $5 user2 $7 {"name":"李四"}
*3 $4 INCR $6 counter $1 1
...
```

重启时**从头到尾重放一遍**，就恢复到最新状态。

### 三种刷盘策略（`appendfsync`）——这是最关键的一行配置

| 策略 | 行为 | 丢多少 | 性能 |
|---|---|---|---|
| **`always`** | 每条命令都 `fsync` 落盘才返回 | **几乎不丢** | 最差（每写一次就来一次磁盘同步，QPS 可能掉到几千） |
| **`everysec`**（默认推荐） | 先写内存/OS 缓存，**后台每秒 fsync 一次** | **最多丢 1 秒** | 好（fsync 在后台线程，不阻塞主线程） |
| **`no`** | 只写 OS 缓存，何时落盘由内核决定（通常 30s） | 可能丢 30 秒 | 最好，但不可控 |

**面试要点**：`everysec` 是"性能与可靠性的最佳平衡点"，它把 fsync 交给后台 `bio` 线程做，主线程不阻塞。绝大多数生产环境用它。

### 缺点：文件会无限变大

```
每次 INCR counter 10 次 → AOF 里就有 10 条命令
但实际只需要一条 SET counter 10
```

所以需要 **AOF rewrite（重写）**：

```
BGREWRITEAOF
  → fork 子进程
  → 子进程遍历当前内存，直接生成"等价的最简命令集"（RDB 思路）
  → 同时，父进程把重写期间的新写入追加到 aof_rewrite_buf
  → 子进程写完，父进程把 buf 里的增量补进去，原子替换旧文件
```

这里有两个容易忽略的细节：

- **重写期间新写入不会丢**：靠 `aof_rewrite_buf` 这个缓冲区承接，最后补写。
- **重写期间内存会上升**：既有一份旧 AOF 缓冲，又有一份 rewrite buf。

### AOF 优点 / 缺点

| 优点 | 缺点 |
|---|---|
| 丢数据少（1 秒） | 文件大，**恢复慢**（重放命令，1000 万条可能几分钟） |
| 是"可读文本"，出问题能人工修复（如误删 flushall 后抢救） | 持续写盘有 IO 开销 |
| 追加写，顺序 IO，性能好 | rewrite 时 fork + COW 开销 |

## 3. 混合持久化（Redis 4.0+）：把两者的优点合起来

配置：

```
aof-use-rdb-preamble yes
```

此时 AOF 文件结构变成：

```
┌────────────────────┬─────────────────────────┐
│  前半部分：RDB 格式  │  后半部分：增量命令(AOF)  │
│  （快照，加载快）    │  （重写之后的写入）       │
└────────────────────┴─────────────────────────┘
```

**效果：恢复速度接近 RDB（前半直接加载），丢数据量接近 AOF（后半逐条重放，最多 1 秒）。**

> 加分点：Redis 7.0 又升级成 **Multi-Part AOF**，把 RDB preamble、增量 AOF、manifest 拆成多个文件（`appendonlydir/` 目录）。好处是解决 4.0 混合模式的两个问题：一是重写时文件巨大导致拷贝慢，二是崩溃后修复整个大文件很慢。7.0 只需重写增量部分。

## 4. 三种方案对比（背这张表）

| 维度 | RDB | AOF (everysec) | 混合 |
|---|---|---|---|
| 丢数据 | 分钟级 | **≤1s** | ≤1s |
| 恢复速度 | **快** | 慢 | 快 |
| 文件大小 | **小** | 大 | 中 |
| 写入开销 | 低（周期性） | 中（持续） | 中 |
| 适用 | 备份、缓存、主从 | 存储型 | **生产首选** |

**生产选型建议**：

| 场景 | 配置 |
|---|---|
| 纯缓存（丢了能回源） | 可以**完全关闭持久化**，或只留 RDB 做冷备 |
| 有存储属性（如 session、排行榜） | `appendonly yes` + `everysec` + `aof-use-rdb-preamble yes` |
| 极端可靠性（不能丢一条） | `always`，但要接受 QPS 下降，且**通常不该用 Redis 承担这种数据** |

## 5. 重点：fork + COW 到底发生了什么

这是全文的核心，分四步讲。

### 第一步：`fork()` 做了什么

Redis 做 bgsave / bgrewriteaof 时会 `fork()` 一个子进程。

```
fork 之前：
   父进程（Redis 主进程）持有 10GB 数据在物理内存里

fork 瞬间：
   内核复制父进程的【页表】（不是复制数据！）
   → 子进程拿到一份完全相同的页表
   → 父子进程的虚拟地址都指向【同一批物理页】
   → 这些页被标记为【只读】（read-only）
```

**关键：fork 那一刻几乎不复制数据，只复制页表。** 所以 fork 是"廉价"的——这是它能被用作快照机制的原因。

但要理解页表本身有多大：

```
10GB 数据 / 4KB 每页 = 约 262 万个页
每个页表项（PTE）约 8 字节
页表总大小 ≈ 262 万 × 8B ≈ 21MB
```

所以 fork 要复制并建立 20 多 MB 的映射结构，**耗时与内存大小成正比**。

这就是 Redis 官方说的 **"fork 是 O(n)，n 是页表大小"**。

实测量级：10GB 实例 fork 耗时 **20~50ms**（`INFO stats` 里的 `latest_fork_usec` 能看到，单位微秒）；20GB 可能到 100ms 以上。

> **这几十毫秒里 Redis 主线程是阻塞的，不能处理任何命令。** 这是 RDB/AOF rewrite 引起延迟毛刺的根源。所以"大实例 + 频繁快照 = 周期性卡顿"。

### 第二步：写时复制（Copy-On-Write）

fork 之后，父子进程共享物理页，但这些页是只读的。**任何一方要写，内核必须先把那一页复制一份。**

```
场景：父进程（Redis 主进程）收到一条 SET 命令，要修改页 A

   内核发现页 A 是共享且只读的
        ↓
   分配一个新物理页 A'，把 A 的内容复制过去
        ↓
   父进程的页表指向 A'，子进程仍然指向 A
        ↓
   父进程在 A' 上完成写入
```

**结果：父进程看到新数据，子进程（快照）看到旧数据——快照的一致性就是这么保证的。**

```
fork 之后，父进程写了 3 个页：

   子进程视角：[页A(旧)][页B(旧)][页C(旧)][页D]...
   父进程视角：[页A'(新)][页B'(新)][页C'(新)][页D]...
                        ↑ 这三个页现在有【两份】物理副本
```

### 第三步：所以内存会涨多少？给公式

**内存增量 ≈ 快照期间被修改的页数 × 页大小**

```
物理内存增量 = 写入涉及的页数 × 4KB
```

举例：

| 场景 | 内存增量 |
|---|---|
| 10GB 实例，快照期间写入很少（改 10% 的页） | +1GB |
| 10GB 实例，快照期间写入很多（改 50% 的页） | **+5GB** |
| 10GB 实例，快照期间几乎全量更新 | **+10GB（翻倍）** |

**注意一个容易说错的点**：`INFO memory` 里的 `used_memory_rss` 在 fork 期间看起来"翻倍"了，是因为**父子进程的 RSS 统计各自都算上了共享页**。但真实物理内存增量只等于被改写的页。面试时要能说清这个区别，否则会被追问倒。

**结论：写入越猛、快照周期越长，COW 复制越多。** 所以：

- **不要在写高峰做大快照**
- **实例越大，COW 的绝对增量越大**

### 第四步：单实例为什么要 ≤10~16GB、为什么预留 50% 内存、为什么要关 THP

这四件事是同一套约束的四个面：

**① 单实例 ≤ 10~16GB**

| 原因 | 说明 |
|---|---|
| fork 阻塞时间 ∝ 内存 | 20GB 实例 fork 200ms，直接顶到接口超时 |
| COW 增量 ∝ 内存 | 大实例一次快照可能多吃 10GB |
| 主从同步代价大 | 全量同步要传一个巨大的 RDB |
| 故障恢复慢 | 加载 20GB RDB 要几十秒，期间不可用 |

所以**大内存场景应该用 Cluster 分片成多个小实例**，而不是一个 64GB 巨无霸。这也是 Cluster 存在的实际价值之一。

**② 预留 50% 内存（`maxmemory` 只配 50%~60%）**

```
物理内存 32GB
  maxmemory = 16GB（或 60% ≈ 19GB）
  剩下的留给：COW 副本 + 碎片 + 客户端缓冲区 + 子进程开销 + 系统
```

**如果不预留会怎样：** 快照期间 COW 把内存顶到物理上限 → 触发 **OOM Killer 杀掉 Redis**，或者**开始用 swap**。

Swap 对 Redis 是致命的：数据一旦被换到磁盘，**每次访问都变成磁盘 IO**，延迟从 100μs 变成 10ms 以上，整个 Redis 卡死（甚至引发主从切换）。

配置建议：
```
maxmemory 16gb            # 物理内存的一半左右
maxmemory-policy allkeys-lru
vm.swappiness 1           # 尽量不用 swap
```

**③ `vm.overcommit_memory = 1`**

```
echo 1 > /proc/sys/vm/overcommit_memory
```

为什么必须设？fork 时内核要为子进程"预留"与父进程等量的虚拟内存（因为理论上 COW 之后可能真的要用这么多）。Linux 默认的启发式 overcommit 策略可能判定"内存不够"→ **fork 失败**→ Redis 日志报：

```
Background save may fail due to fork: Cannot allocate memory
```

设成 1 表示"内核无条件允许超额分配"，因为 COW 实际上不会真的用掉那么多。

**④ 关闭 THP（Transparent Huge Pages）**

```
echo never > /sys/kernel/mm/transparent_hugepage/enabled
```

THP 会把内存页从 **4KB 合并成 2MB 大页**。对 Redis 是灾难：

| 问题 | 原因 |
|---|---|
| **COW 复制单位变大 512 倍** | 只要改 2MB 页里的 1 个字节，就要复制一整个 **2MB**。写一点数据，内存就暴涨 |
| **fork 和 COW 延迟飙升** | 复制 2MB 比 4KB 慢得多，毛刺明显 |
| **内存浪费** | 页内未使用的部分也占物理内存 |

Redis 官方在 `redis.conf` 里都写了一句：

```
WARNING: Be sure to disable THP (transparent huge pages) ...
```

顺带：官方建议同时关掉 `defrag` 与 THP 的配合问题，`activedefrag` 在大页下也表现异常。

## 6. 生产配置示例（可直接参考）

```conf
# 内存
maxmemory 16gb                     # 物理 32GB 的一半
maxmemory-policy allkeys-lru

# 持久化
appendonly yes
appendfsync everysec               # 关键
aof-use-rdb-preamble yes           # 混合持久化
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

save 900 1                         # RDB 仅作冷备
save 300 10
dbfilename dump.rdb
dir /data/redis

# 快照期间的保护
repl-backlog-size 64mb             # 写多场景调大
```

系统层：
```bash
vm.overcommit_memory = 1
vm.swappiness = 1
# THP: never
# 关闭 swap 或严格限制
ulimit -n 65535
```

## 7. 监控这几个指标（面试加分）

```
INFO stats
  latest_fork_usec          # 最近一次 fork 耗时（微秒）—— 超过 100ms 要警惕
  rdb_last_bgsave_status    # ok / err
  rdb_last_bgsave_time_sec  # 上次快照耗时
  aof_rewrite_in_progress

INFO memory
  used_memory               # Redis 自己统计的逻辑内存
  used_memory_rss           # 操作系统看到的物理内存（含 COW 共享）
  mem_fragmentation_ratio   # rss/used，>1.5 说明碎片严重
```

**判断套路**：

- `latest_fork_usec` 持续上升 → 实例太大，该分片
- `used_memory_rss` 远大于 `used_memory` 且回落慢 → COW 或碎片，检查是否刚做过快照
- 周期性 RT 毛刺，且与 `rdb_last_bgsave_time` 时间点吻合 → 就是快照的 fork 阻塞

## 8. 三个真实事故模式

**① 快照期间 OOM 被杀**
32GB 机器上跑 24GB 的 Redis，没预留 COW 空间 → bgsave 期间内存顶满 → OOM Killer 干掉 Redis → 主从切换。**根因是没有预留 50%。**

**② 开 THP 导致延迟毛刺**
一个 8GB 实例，每次 bgsave 都有 300ms 的 RT 尖刺，查了半天以为是网络问题，最后发现是 THP 让 COW 复制 2MB 页。关掉后毛刺降到 20ms。

**③ AOF rewrite 循环触发**
`auto-aof-rewrite-percentage 100` 配得太激进 + 写入量巨大 → 刚重写完文件又涨到 100% → 又重写 → CPU 和 IO 长期打满。调大阈值或降低写入量。

## 9. 30 秒面试话术

> "Redis 持久化有两条路。RDB 是某一刻的全量快照，文件小、恢复快，适合备份和主从同步，但只能保证分钟级，两次快照之间的写入会丢。AOF 是追加命令日志，appendfsync 有 always、everysec、no 三档，everysec 是默认推荐，靠后台线程每秒 fsync，最多丢 1 秒，但文件会越来越大需要 rewrite，而且恢复要逐条重放所以慢。生产一般用 4.0 的混合持久化，AOF 文件前半是 RDB 格式保证恢复快，后半是增量命令保证丢得少。

> 真正的坑在 fork 加 COW。fork 只复制页表不复制数据，所以很便宜，但耗时与内存大小成正比，10GB 大概二三十毫秒，这期间主线程是阻塞的，就是延迟毛刺的来源。fork 之后父子共享只读页，父进程一写就要复制那一页，所以内存增量等于快照期间被修改的页数乘以 4KB，写得多的话最坏会翻倍。由此推出三条生产约束：第一，单实例不要超过 10 到 16GB，大的用 Cluster 分片，否则 fork 慢、COW 增量大、恢复也慢；第二，maxmemory 只配物理内存的 50% 到 60%，给 COW 留余量，否则会触发 OOM Killer 或者用 swap，swap 对 Redis 是致命的；第三，必须设 vm.overcommit_memory=1 防止 fork 失败，并且关闭 THP，因为大页会把 COW 的复制单位从 4KB 放大到 2MB，延迟毛刺会非常明显。"

## 10. 可能的追问延伸

| 追问 | 要点 |
|---|---|
| "主从全量同步和 fork 有关吗？" | 有。主节点 `bgsave` 生成 RDB 再传，同样有 fork 阻塞和 COW 开销；传输期间新写入存在 `repl-backlog` 里增量补发 |
| "为什么不能用 Redis 存不能丢的数据？" | `everysec` 也有 1 秒窗口；`always` 会严重拖低 QPS；且 Redis 是异步复制，主节点宕机时未同步的数据会丢 |
| "AOF rewrite 期间写入怎么不丢？" | `aof_rewrite_buf` 缓冲增量，子进程完成后由父进程补写进新文件 |
| "Redis 能当消息队列吗？" | 能（Stream），但持久化语义、消费确认、堆积能力都远不如 Kafka，别用来扛核心链路 |
| "关掉持久化行不行？" | 纯缓存可以，但重启后缓存全空 → **缓存雪崩**打向 DB，必须配合预热和限流 |

---

一句话记住：**RDB 和 AOF 回答"丢多少数据"的问题；fork + COW 回答"为了不丢数据要付多少代价"的问题——而 Redis 的所有容量规划（实例大小、内存预留、THP、overcommit）都是在给这个代价买单。**
