# 热词预热 + IK 动态词库：一篇讲透

这是搜索模块里两个配套的小功能，合起来解决一个问题：**让搜索"越搜越准"**。我拆开讲，先补背景知识。

---

## 〇、先补背景：什么是"分词"，为什么是个问题

ES 检索中文前，必须先把句子**切成词**才能建倒排索引：

```
"招配菜师傅" → 切分 → [招, 配菜, 师傅]   ← 理想情况
"招配菜师傅" → 切分 → [招, 配, 菜, 师傅]  ← IK 不认识"配菜"时的惨状
```

切错的后果：求职者搜"**配菜**"，倒排索引里根本没有"配菜"这个词（只有"配"和"菜"），**这条岗位搜不出来**——明明在招人却没人来应聘。

IK 是 ES 的中文分词插件，内置通用词典。但它不认识**行业黑话**：餐饮的"配菜、打荷、上什、水台"，医疗的"月嫂、护工、陪检"——这些恰恰是招聘搜索里最高频的词。怎么办？IK 支持**远程扩展词库**：你给它一个 URL，它每隔约 1 分钟去拉一份词表，词表里有的词就整体切分。**IK 动态词库 = 做这个 URL 接口的**。

---

## 一、热词预热：是什么、干嘛的

**是什么**：把用户最近搜得最多的关键词统计出来（TopN 热搜榜），提前放进缓存。

**干嘛的**（三个用途，一个比一个重要）：

1. **业务用途**：小程序搜索框下面要展示"热门搜索：厨师、服务员、护士…"——这个榜单就是它；
2. **性能用途**："预热"二字的本意——热词榜是**热点数据**，如果每次展示都现查 Redis/DB，热词榜自己就成了被高频打的热点。定时提前算好放进本地缓存，用户来读时**零成本**（这也是防"击穿"的标准手段）；
3. **喂给 IK**：热词就是"最近用户真实在搜的行业词"，正是 IK 词典缺的词（第二个功能的原料）。

**怎么实现**（[HotKeywordService](/C:/Users/root/.zcode/workspace/draft-8044cc21-7e3b-4c13-a29d-9540f2f8cc42/store-quickhire/src/main/java/com/youhan/quickhire/module/home/service/HotKeywordService.java)，三步流水线）：

```
① 埋点(每次搜索)          ② 定时聚合(每60秒)           ③ 读取(随时)
search("厨师")            @Scheduled                   /api/search/hot
   ↓                         ↓
ZINCRBY hot:zset 厨师 +1   ZREVRANGE 取 Top20
   ↓                         ↓
(Redis ZSet:              写入 Caffeine 本地缓存 ←────── 直接读本地缓存返回
 词→热度分)                    (预热完成)
```

对应代码就三个方法：

```java
// ① 埋点: SearchController.search() 里调用, ZSet 里该词热度+1
public void record(String keyword) {
    stringRedisTemplate.opsForZSet().incrementScore(HOT_ZSET_KEY, keyword.trim(), 1);
}

// ② 定时聚合: 每 60 秒把 TopN 算好塞进本地缓存 = "预热"
@Scheduled(initialDelay = 10_000, fixedDelay = 60_000)
public void preheat() { refreshTopCache(); }   // ZREVRANGE 0..19 → localCache.put

// ③ 读: 优先读预热好的本地缓存, 没有才现场算一次
public List<String> topKeywords() {
    Object cached = localCache.getIfPresent(TOP_CACHE_KEY);
    if (cached instanceof List) return (List<String>) cached;
    return refreshTopCache();
}
```

**为什么用 Redis ZSet**：ZSet（有序集合）天生就是干排行榜的——`ZINCRBY` 加热度、`ZREVRANGE` 按分数取前 N，都是 O(logN)。对比用 MySQL `ORDER BY count`：每次搜索都 UPDATE 一行再排序，高频小写入会把数据库拖死。

**管理端加权**：`addWord()` 一次 +100 分，运营手动让"护士"置顶——业务上的推广位。

## 二、IK 动态词库：是什么、干嘛的

**是什么**：一个 HTTP 接口 `GET /api/search/dict`，按行返回词表文本；ES 的 IK 插件定期来拉，**词表变了分词效果就变，不用重启 ES**。

**干嘛的**：把上面说的"行业黑话"喂给 IK，解决"配菜"被切碎的问题——这是**搜索准确率**的事。

**怎么实现**（[SearchController.dict](/C:/Users/root/.zcode/workspace/draft-8044cc21-7e3b-4c13-a29d-9540f2f8cc42/store-quickhire/src/main/java/com/youhan/quickhire/module/search/controller/SearchController.java)）：

**接口端**（我们写的，全项目就这一个方法）：

```java
@GetMapping(value = "/dict", produces = "text/plain;charset=UTF-8")
public ResponseEntity<String> dict(@RequestHeader("If-None-Match") String ifNoneMatch) {
    String content = hotKeywordService.dictContent();     // 热词按行拼成文本: "厨师\n服务员\n护士\n"
    String etag = "\"" + DigestUtil.md5Hex(content) + "\"";  // 内容指纹
    if (etag.equals(ifNoneMatch)) {
        return ResponseEntity.status(HttpStatus.NOT_MODIFIED).build();  // 词没变 → 304 空响应
    }
    return ResponseEntity.ok().eTag(etag).body(content);   // 词变了 → 200 + 新词表
}
```

**ES 端**（不是 Java 代码，是 IK 插件的配置，一行）：

```xml
<!-- ES 容器内 /usr/share/elasticsearch/config/analysis-ik/IKAnalyzer.cfg.xml -->
<entry key="remote_ext_dict">http://我们的服务/api/search/dict</entry>
```

配好后 IK 自己每约 1 分钟轮询这个 URL，**词表内容一变就热加载进分词词典**——整个过程不重启 ES、不重建索引。

**ETag/304 是怎么回事**（HTTP 协议的省钱技巧）：IK 每分钟来拉一次，但词表大多数时候没变。我们用**内容的 MD5** 当 ETag（指纹）；IK 第一次拿到词表时记下 ETag，下次请求带上 `If-None-Match: "指纹"`——服务端比对指纹没变就回 **304 Not Modified（空 body）**，不传词表内容。轮询一年，流量几乎为零；词一变指纹必变，立刻拉到新词表。

## 三、两个功能怎么串成一个闭环（精髓在这）

```
用户搜"打荷" → ① ZINCRBY 埋点, "打荷"热度+1
                    ↓ 60秒后
              ② 定时任务聚合: "打荷" 进 TopN
                    ↓
              ③ /api/search/dict 内容变了 → ETag 变了
                    ↓ IK 下次轮询(约1分钟)
              ④ IK 拉到新词表, "打荷" 整体进词典
                    ↓
              ⑤ 下次有岗位含"打荷" → 切分正确 → 搜"打荷"能搜到
```

**用户的真实搜索行为，驱动了分词词典的自动进化**——冷门行业词不用人工维护词库，搜的人多了自动成为词条。这就是简历上"热点关键词预热及自定义分词库动态刷新"这句的完整含义：**热词预热是上半程（统计+缓存），IK 动态词库是下半程（喂给分词器），中间靠 ETag 热更新连接**。

---

## 四、面试速答

| 追问 | 答案 |
|---|---|
| 热词为什么用 ZSet | 排行榜天然结构：ZINCRBY 加分 / ZREVRANGE 取 TopN 都 O(logN)；DB 扛不住高频小写入 |
| "预热"预的是什么 | 把 TopN 提前算好放本地缓存——热词榜自己是热点，避免每次现查、防击穿 |
| 词库为什么要动态 | 新词（行业黑话、新梗）不断出现，静态词典必然滞后；热更新免重启 ES |
| IK 怎么知道词变了 | 它每约 1 分钟轮询 remote_ext_dict 接口，比对内容 |
| ETag/304 图什么 | 轮询频率高但内容少变，MD5 指纹比对，没变就空响应，省 99% 流量 |
| 词表格式 | text/plain，每行一个词（IK 的约定格式） |
| 效果怎么验证 | `_analyze` API 对比：加词前"配菜师傅"切成"配/菜/师傅"，加词后"配菜/师傅" |
| 词表存哪 | 热词在 Redis ZSet；接口现拼文本。更完整的做法是词库落库+版本号管理 |

**一句话总结**："热词预热是把用户搜出来的热词统计好、缓存好；IK 动态词库是把这些热词自动喂给 ES 分词器，让分词效果跟着用户需求热更新——串起来就是'搜索行为驱动搜索质量'的闭环。"
