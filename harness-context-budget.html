把最后一列连起来看：五家指向「再来一次读」，只有一家指向「换个动作」。而 grep 这个能力，五家其实都有——Claude Code 有 Grep，Gemini CLI 有 search_file_content，OpenCode 有 grep/glob，SWE-agent 有 search_file。缺的不是工具，是提示里那句话。

你的底座长什么样：三层边界

第一层 · pi 上游：2000 行 / 50 KB 头截 + offset 续读 → 复用的，不是自研
第二层 · 宿主 wrapper：设备与二进制守卫、PDF/notebook/video 分派、24 KB 二次截断、重写续读提示 → 多数改动在这里
第三层 · 设计方案：落盘 + 句柄 + 截断即告知 → 只在讲解文档里，快照里没有
模型真正看到的线是 24 KB（output-limit.ts:4），不是 pi 的 50 KB。所以绿条其实应该更短——前提是它真的落在代码里。

机制还是策略：这才是你和他们的分野

业界做法 · 写进 prompt

「先 grep 定位，再读片段」写进 system prompt。Claude Code 起家就是 glob + grep，Cursor 有 codebase_search。

代价：建议可以被忽略。截断提示还在说 Use offset=N，模型顺着提示往下读最省事。

你的做法 · 写进返回值

截断这件事本身成为 Tool Result 的一部分：内容被切了、全文在这、用关键词来取。

代价：落盘要付 TTL / 租户 / 回收；多一轮检索；而且快照里还没落地。

所以那句「别人不做检索」站不住——别人做的是策略，你做的是机制。策略是建议，机制是返回值的一部分，模型绕不过去。这个差别站得住，也经得起一句反问。

两个 review 必问的问题

为什么是 50 行，不是剩余预算
Claude Code 的 allow_large 是按「会话剩余上下文」读全文件的。窗口是全局资源，只有运行时知道还剩多少——工具层的硬阈值要有理由。
入口都覆盖住了吗
Gemini CLI 的 ACP 路径曾整个绕过 truncate，一次 24 MB 输出打爆 1M 输入。你自己 PTC 通道的 8 MiB 上限是同一类洞。
合上页面前，试着答一下
  1. 如果模型就是不 grep、一路续读，你的方案退化成哪一档？还省吗？
  2. 「50 行预览」在没有落盘的情况下，还剩多少价值？
  3. 94.5% 的分母，应该按工具返回值算，还是按模型实际收到的字符串算？
